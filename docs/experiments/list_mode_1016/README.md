# 목록·동향 질문 모드 (사전 등록, 2026-10-16)

> 측정 **전에** 쓴다. 출발점: [`status_1015/`](../status_1015/) §5 성적표 — 주제 목록·동향 D(real40 정답 인용 ≥ 3: 1/8).

## 0. 진단 (2026-10-16, `.cron/list/diag.py`, 검색만 · 맥미니)

목록(T) 16문항(real40 8 + real2 8)은 정답 논문이 8~90편인데 운영 컨텍스트에는 3~5편뿐이다. 세 군데가 묶고 있다.

1. **검색 편수:** 라우터가 `RAG_TOP_K=3` 으로 먼저 검색하고 답변 노드가 그 결과를 재사용한다(목록 질문도 마찬가지). 답변 노드의 `top_k=15` 는 거의 쓰이지 않는다.
2. **블록 수 · 길이:** 답변 노드가 `_rag_context_top_n_hits(n=5)` 로 5블록까지만 넘기고, 블록마다 초록(이제 최대 2,000자) + 본문 1,200자다. 8편만 넣어도 ~28,000자.
3. **항목 상한:** 답변 프롬프트가 "본론 항목 2~4개", `min(doc_count, 4)` 로 묶는다.

top_k 를 늘리면 컨텍스트 안 정답이 크게 는다 (16문항 합, 같은 검색어):

| top_k | 3 | 8 | 15 | 25 |
|---|---|---|---|---|
| 컨텍스트 안 정답 (합) | 23 | 50 | 103 | 151 |

- 게이트(`gate_types`)는 16문항 모두 `list` 로 잡는다. 162 에서 `list` 는 A015 · C1_02 두 문항뿐.
- **제약:** 답변 모델 Ollama `n_ctx` 는 4,096 토큰이다(로그). 최근 프롬프트 최대 3,533 토큰. 10-13 이후 4,096 벽에 닿은 생성 0건(그 전 로그 244건) — 지금 문제는 없지만 여유가 적다. 그래서 편수를 늘리되 **블록을 짧게** 해 전체 길이를 지금 수준으로 묶는다.

## 1. 바꾸는 것 — `RAG_LIST_MODE` (기본 `0`)

`1` 이고 질문이 `list` 게이트에 걸리면(단일 히트 요청 제외) 답변 노드에서:
1. 라우터 컨텍스트를 재사용하지 않고 **`top_k=10` 으로 다시 검색**한다(같은 검색어, light rerank 설정은 운영과 같게).
2. 블록을 **짧게**: 머리(`[ID] 제목`) + 초록 앞 500자, 본문 청크는 뺀다.
3. 넘기는 블록 수 상한 5 → **10**, 본론 항목 상한 `min(doc_count, 4)` → **`min(doc_count, 8)`**, 항목마다 1~2문장으로 쓰라고 지시한다.

비교 분리 검색(`cmp`)이 함께 걸리는 문항(T07 등)은 그 처리를 그대로 둔다(목록 모드의 검색 결과에 대상 블록을 앞에 합친다).

## 2. 방법

운영 `.env` 그대로(`eval_e2e_ko.py --answer --save-context`), 같은 DB·같은 시간대에 대조 `lm0_*`(`RAG_LIST_MODE=0`) · 처리 `lm1_*`(`=1`) 번갈아. 목록 모드는 `list` 게이트 문항에만 영향을 주므로 **게이트 문항만** 잰다: real40 · real2 의 `list` 게이트 문항(T 16 + 그 밖에 걸리는 문항) + 162 의 A015 · C1_02. 비게이트 문항은 코드 경로가 같다(단위 테스트로 확인).

- 문항 수가 작다(T 16). 효과 방향은 한쪽으로만 나왔다(악화 0).
