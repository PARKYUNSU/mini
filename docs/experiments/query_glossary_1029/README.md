# 일상어 → 분야 용어 사전을 검색어 뒤에 붙이기 (사전 등록, 2026-10-29)

> 측정 **전에** 쓴다. 출발점: query_example_1029 — R_134 에서 검색 결과를 가른 것은 쉼표 · 순서가 아니라 **단어**였다. 9B 검색어 LLM 은 "중복 내용"을 `duplicate content detection` 으로 직역하고 분야 용어 `near-duplicate detection · deduplication` 을 못 만든다(external_term_1029 에서도 직역). 사용자 직무는 LLM · RAG — 질문 속 RAG 는 지우지 않는다.
> 앞 실패에서 배운 것: 검색어를 통째로 바꾸면(query_extract_1021 v2) 162 ok 135 → 119 로 무너졌다. 그래서 **검색어는 그대로 두고 용어만 뒤에 붙인다.**

## 1. 바꾸는 것 — `RAG_QUERY_GLOSSARY=1` (기본 0)

`core/rag/query_glossary.py` `add_field_terms(질문, 검색어)` — 사전 21항목(한국어 정규식 → 영어 분야 용어, 측정 전 고정). 질문에 키가 있고 검색어에 그 용어(첫 단어)가 없으면 `, <용어>` 를 붙인다. 최대 2개. 한국어 폴백 검색어는 건드리지 않는다. `agent_nodes._extract_english_rag_query` 끝에서 부른다(라우터 · 답변 노드 · 외부 검색 모두 같은 검색어). 단위 테스트 `tests/unit/test_query_glossary.py`.

사전이 작동하지 않는 문항은 검색어가 같다 → 컨텍스트도 같다. 그래서 **작동하는 문항만** 잰다.

## 2. 측정 — 검색만(`--save-context`), 대조 `qg0_*` · 처리 `qg1_*`(`RAG_QUERY_GLOSSARY=1`)

- **G 16**(`g_questions.tsv`) — 이 사전 등록과 함께 새로 쓴 LLM · RAG 일상어 질문(사전을 쓴 뒤 써서 키에 맞춰졌을 수 있음 — 한계).
- **sub 7**(`sub_questions.tsv`) — 기존 세트에서 사전이 작동하는 문항(ce1 · rr1 검색어로 셈): 162 A061 · A077 · A117, real40 R04, H19, D07 · D12. 기존 세트 나머지 391문항은 검색어가 그대로라 재지 않는다(H · D · U 98 중 3, 162 중 3, real40 중 1, real2 0).
- **er 12**(corpus_er_1029) — 사전을 쓸 때 본 질문이라 **표본 안, 보고만**.
- 관련성 판정: 두 조건 컨텍스트 쌍을 섞어 조건 모른 채 0 · 1 · 2.

## 3. 판정 (측정 전 고정)

| 지표 | 기준 |
|---|---|
| **주:** G + sub 중 처리에서 검색어가 실제로 바뀐 문항 — 질문별 '2' 수 | 처리 > 대조, 부호 검정(동점 제외) 양측 p < 0.05 |
| 보호: sub 중 정답 있는 문항(162 · real40 4개) 검색 ok | 처리가 대조보다 2 이상 낮지 않음 |
| 보호: 주 지표 문항 '0' 합 | 처리 ≤ 대조 × 1.5 |
| 보호: 검색어 안 바뀐 문항 | 대조 · 처리 검색어 같음(구현 확인) |
| 보고: 작동률(G 16 중 바뀐 수) · er 12 같은 지표 · R_134 | |

채택이면 사용자 승인 후 운영 `.env` 반영 + 봇 재시작.

예상: 작동 문항이 적어(G 에서 8~12 · sub 7) 유의하려면 거의 전부 좋아져야 한다. 9B 가 이미 쓰는 용어(hallucination · citation · reranking 등)는 첫 단어 검사로 안 붙는다 — 작동률이 생각보다 낮을 수 있다. 붙인 용어가 원래 검색어 뜻을 묽게 해 '2' 가 줄 위험도 있다.
