# 한국어 끝단 평가 — 질문이 LLM 컨텍스트에 정답 논문을 싣는가 (사전 등록)

- 시작일: 2026-10-08
- 선행: [`../retrieval_eval_1007/05_conclusion.md`](../retrieval_eval_1007/05_conclusion.md) §11 — 검색 평가셋(영어 검색어 직접 투입)이 재지 않는 단계에서 운영 버그 둘(이전 턴 컨텍스트 재사용, 한국어 검색어 폴백)이 나왔다.
- **이 라운드는 기준선이다 — 판정 없음.** 앞단(라우팅·검색어 추출·상태 관리)을 고칠 때 쓸 자와 현재 값을 만든다.

## 1. 무엇을 재나

한국어 질문 → `router_node` → (`direct_answer` / B 이면) `direct_answer_node` 의 검색어 추출·검색·컨텍스트 조립까지 **운영 노드를 그대로** 실행하고, 답변 LLM 호출만 가로챈다. 지표는 **LLM 에 건네진 `[문서 N]` 번호표에 정답 논문이 있는가** (`number_context_papers` 의 doc_ids — 청크 본문에 인용된 ID 는 세지 않는다). 답변 품질은 재지 않는다.

## 2. 문항

[`ko_questions.tsv`](ko_questions.tsv) · 164문항 · sha256 `7fc27b9d5bc9` — `retrieval_eval_1007` 의 A·C1·C2 를 사용자 말투의 한국어 질문으로 옮겼다 (정답은 같은 `eval_set.jsonl`). 기술 용어(LLM, RAG, CLIP …)는 실제 사용자처럼 영어로 둔다. "검색"이라는 단어가 든 문항 9개 — 인위적으로 빼지 않았다. `A026`·`A057` 은 정답이 Chroma 에 없어 제외 → **162문항**.

파일럿 3문항(`A063`·`C1_07`·`C2_03`, 하네스 확인용)은 결과에 넣지 않는다. 파일럿 후 문항은 바꾸지 않았다.

## 3. 측정

```bash
.venv/bin/python scripts/eval_e2e_ko.py --label prod_r1
.venv/bin/python scripts/eval_e2e_ko.py --label prod_r2
```

- 문항마다 새 chat_id, 앞뒤로 `clear_session` — 세션 오염 없음.
- 실패 라벨: `route`(direct_answer/B 아님) · `query_korean`(검색어에 한글) · `retrieval`(컨텍스트에 정답 없음) · `no_context`.
- **검색어 추출(로컬 LLM, temperature 0.2)과 라우터 3단계 LLM 분류는 비결정적이다.** 파일럿에서 `C1_07` 이 실행마다 적중이 갈렸다. 그래서 2회 잰다: **주 수치는 `prod_r1`**, `prod_r2` 는 문항별 적중이 두 번 사이에 바뀌는 비율(흔들림)을 재는 데만 쓴다.

## 4. 보고할 것 (판정 없음)

1. 162문항 컨텍스트 적중률 (층별).
2. 실패 원인 분포 — 특히 `route` 몇 개가 어느 경로로 샜는지.
3. **같은 문항의 검색 단계 성능과의 차** — `retrieval_eval_1007/results/fix3_lr/production.jsonl`(영어 검색어, Recall@5)과 짝지어: 검색 단계에서는 맞혔는데 끝단에서 놓친 문항 수 = 앞단 손실.
4. r1–r2 흔들림 비율. 이후 앞단 수정의 효과를 판정할 때 이 크기보다 작은 차이는 해석하지 않는다.

## 5. 예상 (기록만)

- 끝단 적중률은 검색 단계(0.951)보다 낮다. 앞단 손실의 다수는 `route` 일 것이다.
- 컨텍스트가 1편으로 줄어드는 경로(`prefer_single_hit`)가 "논문 요약해줘"류에서 정답을 잃게 만든다.

## 6. 결과 (2026-10-08)

| | r1 | r2 |
|---|---|---|
| 컨텍스트에 정답 (162) | **0.074** (12) | 0.068 (11) |
| 경로 direct_answer/B (RAG) | 18 | 17 |
| use_existing_tool (Tavily 등) | 89 | 89 |
| direct_answer/A (잡담) | 50 | 47 |
| planner/C | 5 | 9 |

흔들림: 두 실행 사이에 적중이 바뀐 문항 3개 (1.9%). 검색 단계(`fix3_lr`, 영어 검색어)에서 맞혔는데 끝단에서 놓친 문항 **142개** — 그중 137개가 `route`.

### 6.1 기전 — RAG 는 '논문'이라는 단어가 있어야 허용된다

`is_rag_allowed(chat_id, q) = get_paper_mode(chat_id) or ("논문"/"paper"/"chroma"… in q)`. `/paper` 논문 모드는 **기본 OFF 이고 메모리에만 저장돼 봇을 재시작할 때마다 꺼진다.** 모드가 꺼져 있으면 라우터가 RAG(B)로 골라도 `_maybe_override_rag_route` 가 Tavily(사실 조회) 또는 잡담(A)으로 바꾼다.

| 질문에 '논문' | 문항 | RAG 경로 | 정답 |
|---|---|---|---|
| 있음 | 23 | 18 | 12 |
| **없음** | **139** | **0** | **0** |

'논문' 이 있어도 5개(`A010`·`A028`·`C2_02`·`C2_13`·`C2_15`, 전부 "…논문 알려줘")는 하드룰로 도구 경로에 갔다. 2026-10-08 운영 확인의 질문 1·3 이 RAG 로 간 것도 둘 다 '논문'을 담고 있었기 때문이다.

### 6.2 RAG 로 간 18문항 안에서

12/18 (67%) 적중. 놓친 6개 중 5개는 **컨텍스트가 1편뿐**이었다 — "논문 요약해줘/설명해줘" 가 `prefer_single_hit` 로 상위 1편만 남긴다(§5 예상 2 적중). 1개(`A042`)는 컨텍스트 0편.

### 6.3 예상 대조

- 예상 1 (끝단 < 검색 단계, 손실 다수는 route): **맞음** — 0.074 vs 0.951, 손실 142 중 137 이 route.
- 예상 2 (`prefer_single_hit` 가 요약·설명 요청에서 정답을 잃게 함): **맞음** — RAG 내 미스 6 중 5.

### 6.4 해석

운영 기본 상태에서 **논문 지식베이스는 사용자가 '논문'이라고 말할 때만 쓰인다.** 검색 품질(0.951)은 그 좁은 문으로 들어온 질문에만 적용된다. 이것이 의도된 정책(일상 질문의 RAG 오염 방지)인지, 재시작으로 논문 모드가 꺼지는 것이 의도된 것인지는 사용자 결정 사항이다. 다음 측정 후보: (a) 논문 모드 ON 조건에서 같은 162문항 (RAG 경로 자체의 끝단 성능), (b) `prefer_single_hit` 를 끈 조건.

## 7. 논문 모드 ON 조건 (사전 선언, 2026-10-08)

**측정**: `--paper-mode --label paper_r1` — 문항마다 `set_paper_mode(chat_id, True)`. 나머지는 §3 과 같다. 1회 (§6 흔들림 1.9% 로 반복의 이득이 작다).

**보고 (판정 없음)**:
1. 컨텍스트 적중률과 경로 분포. RAG 가 허용돼도 하드룰·LLM 분류가 다른 경로로 보내는 문항이 얼마나 남는지.
2. `prod_r1` 대비 짝지은 차 — 논문 모드가 살리는 문항 수.
3. 검색 단계(`fix3_lr`) 대비 남는 손실을 원인별로 (route / 단일 문서 컨텍스트 / 검색어 / 검색).

**예상**: 경로 손실은 크게 줄지만 0 은 아니다("…알려줘"류 하드룰·planner). RAG 경로 안의 적중률은 §6.2 의 67% 근처이고, 남는 미스의 다수는 단일 문서 컨텍스트(`prefer_single_hit`)다. 전체 적중률 0.5~0.7.

### 7.1 결과 (2026-10-08)

| | 논문 모드 OFF (`prod_r1`) | **ON (`paper_r1`)** |
|---|---|---|
| 컨텍스트에 정답 (162) | 0.074 | **0.716** |
| A / C1 / C2 | 0.042 / 0.083 / 0.250 | 0.712 / 0.917 / 0.500 |
| RAG 경로 | 18 | 149 |

짝지은 비교 ON vs OFF: **104 : 0** (p≈1e-31). 논문 모드가 잃게 한 문항은 없다.

검색 단계(`fix3_lr`)에서 맞혔는데 끝단에서 놓친 39문항의 원인:

| 원인 | 문항 |
|---|---|
| **컨텍스트 1편만 (`prefer_single_hit`)** | **20** |
| 경로 — 도구(Tavily 등) | 6 (`A010`·`A028`·`A046`·`C2_02`·`C2_13`·`C2_15`, 대부분 "…논문 알려줘/설명해줘") |
| 경로 — planner | 5 |
| 경로 — 잡담(A) | 2 |
| 검색 (컨텍스트 여러 편인데 정답 없음) | 6 |

RAG 경로 안에서: 컨텍스트 1편인 62문항 적중 41 (66%) · 여러 편인 86문항 적중 75 (87%).

### 7.2 예상 대조

- 경로 손실이 크게 줄지만 0 은 아니다: **맞음** — 144 → 13.
- 남는 미스의 다수는 단일 문서 컨텍스트: **맞음** — 39 중 20.
- 전체 0.5~0.7: **약간 넘음** — 0.716.

### 7.3 해석

RAG 경로 자체는 끝단에서 0.72 를 낸다. 지금 운영(논문 모드 OFF 기본, 재시작마다 꺼짐)은 0.07 이다. **가장 큰 레버는 검색 품질이 아니라 정책이다.** 그다음은 `prefer_single_hit` (20문항) — 요약·설명 요청에서 상위 1편만 남기는 규칙이 C2(고전 논문) 0.500 의 주원인이다.

## 8. 논문 모드가 잡담·계획을 오염시키는가 (사전 선언, 2026-10-08)

§7 로 논문 모드 ON 이 RAG 끝단을 0.074 → 0.716 으로 올린다는 것을 확인했다. 기본값으로 켜기 전에 반대쪽 비용을 잰다.

**문항**: [`tests/fixtures/local_llm_failure_eval.jsonl`](../../../tests/fixtures/local_llm_failure_eval.jsonl) 의 chat 48 · planner 64 (= 112, 논문과 무관한 일상·작업 요청).

**측정** ([`scripts/eval_route_contamination.py`](../../../scripts/eval_route_contamination.py), 라우터만): `off_a` · `off_b` (모드 OFF 두 번 — 라우터 3단계 LLM 분류의 흔들림 크기) · `on` (모드 ON).

**오염의 정의**: 라우터가 `direct_answer/B` (RAG) 로 보낸 문항. B 로 가면 답변이 논문 컨텍스트와 RAG 템플릿으로 만들어진다.

**판정 (결과 전 고정)**:
- 주: `on` vs `off_a` 의 짝지은 McNemar — 문항별 "B 로 감" 여부.
- 권고 규칙: chat 48 에서 ON 이 B 로 새로 보내는 문항이 **`off_a`–`off_b` 사이 흔들림 수 + 2 이하**이면 "논문 모드 기본 ON" 을 권고한다. 넘으면 기본 ON 대신 (a) 모드를 디스크에 저장만 하거나 (b) 논문 모드 편향 규칙(`_apply_paper_mode_router_bias`)을 좁히는 쪽을 권고한다.
- planner 64 는 같은 방식으로 보고하되, 계획 슬롯 채택 측정(`planner_adopt_1007`)과 무관하다 — 이 측정은 라우팅만 본다.

**예상**: `_apply_paper_mode_router_bias` 는 A→B 를 `is_factual_lookup`·`_paper_knowledge_heuristic`("요약"·"설명" 등) 일 때만 바꾼다. chat 문항 중 "설명해줘"·"알려줘" 류가 걸려 **3~8개**가 B 로 갈 것이다 → 권고 규칙상 기본 ON 은 어려울 가능성이 크다.

### 8.1 결과 (2026-10-09)

| | off_a | off_b | **on** |
|---|---|---|---|
| chat 48 → RAG(B) | 0 | 0 | **9** |
| planner 64 → RAG(B) | 0 | 0 | **8** |
| chat → Tavily 도구 | 7 | 7 | 0 |
| planner → Tavily 도구 | 7 | 7 | 0 |

- 흔들림: off_a–off_b 사이 "B 로 감" 이 바뀐 문항 0 (경로 전체로는 chat 4).
- **chat: ON 이 새로 B 로 보낸 문항 9 : 0 (p=0.0039).** 권고 문턱(흔들림 0 + 2 = 2)을 넘는다 → **사전 규칙에 따라 "논문 모드 기본 ON" 은 권고하지 않는다.**
- planner: 8 : 0 (p=0.0078).
- 새로 B 로 간 17문항 중 13개는 OFF 에서 이미 **Tavily(웹검색)** 로 가던 것이다 — 라우터가 "알려줘·설명해줘·요령" 류를 B 로 고르고, OFF 에서는 `_maybe_override_rag_route` 가 그것을 Tavily 로 바꿨다. 즉 **OFF 에서도 일상 요청 14개(12.5%)가 웹검색으로 새고 있다.** 논문 모드 편향(`_apply_paper_mode_router_bias`, A/C → B)으로 바뀐 것은 4개(`chat_11`·`chat_35`·`chat_46`·`planner_61`).

### 8.2 예상 대조

- "chat 3~8개가 B 로" → **9개**, 예상보다 약간 많다. "기본 ON 은 어렵다" → **맞음.**

### 8.3 해석

문제의 뿌리는 논문 모드가 아니라 **라우터가 B(조회형)를 너무 넓게 고른다는 것**이다. "알려줘·설명해줘" 가 붙은 일상 요청이 B 로 분류되고, 그 뒤 논문 모드가 그것을 RAG 로 보낼지 Tavily 로 보낼지만 정한다. 그래서 논문 모드 ON 은 논문 질문 104개를 살리는 대신 일상 요청 17개를 RAG 로 오염시키고, OFF 는 논문 질문을 버리고 일상 요청 14개를 웹검색으로 보낸다. 두 상태 모두 일상 요청이 엉뚱한 곳으로 간다.

권고 (사전 규칙 §8): 기본 ON 대신 — **RAG 허용 조건을 "'논문' 단어 또는 모드" 에서 "질문이 학술·기술 주제인가" 로 바꾼다.** 끝단 162문항(논문 질문)과 이 112문항(일상·작업)이 바로 그 분류기의 양성·음성 평가셋이 된다.
