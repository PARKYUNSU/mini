# 템플릿 준수는 **언제** 무너지는가 (사전 등록)

- 시작일: 2026-10-06
- 선행: [`../checkpoint_1004/05_conclusion.md`](../checkpoint_1004/05_conclusion.md) §3 (해리) · [`../protocol.md`](../protocol.md) §5.2 개정 · §5.3(4)
- **새 모델을 만들지 않는다.** v9 설정(lr 2e-4 · v9 데이터 · 시드 3407 · 138스텝)을 **그대로** 다시 돌리며 **초반을 촘촘히** 저장한다. `SAVE_STEPS=3` + `SAVE_STEPS_MAX=24`.
- 비용: 학습 1회(~$0.3) · 머지 8회 · 측정 1회(**RAG 슬롯만**, 11모델 ≈ 3시간)

## 1. 묻는 것

[`../checkpoint_1004/05_conclusion.md`](../checkpoint_1004/05_conclusion.md) §3 이 해리를 드러냈다 — lr 2e-4 로 학습하면 **23스텝 안에** RAG 템플릿 준수가 무너지는데(base 3/24 → ckpt23 **19/24**), 같은 지점에서 길이 제약 준수는 꼼짝도 않는다(7 → 8). 두 행동은 같은 현상이 아니다.

**이 라운드는 그 구간을 좁힌다.** 23스텝은 전체의 17%이고 예시 184건이다. 그 안 어디서 무너지는지는 모른다.

**왜 이것이 값이 있나**: 운영 RAG 슬롯이 그 템플릿을 쓴다 (`RAG_OUTPUT_TEMPLATE_MULTI_STRICT`, "아래 뼈대를 그대로 따라 값만 채우세요"). 즉 이 지표는 길이 제약과 달리 **운영이 실제로 의존하는 성질**이다. "파인튜닝이 시스템 프롬프트 준수를 몇 스텝에 잃는가" 는 다음 학습을 언제 멈춰야 하는지에 직접 닿는다.

## 2. 측정 가능성 — §5.2 를 먼저 개정했다

[`../protocol.md`](../protocol.md) §5.2 는 RAG 수치를 판정 근거로 쓰는 것을 금지했다. 입력(검색된 문서)이 고정되지 않기 때문이다. **그 논리는 내용 지표에만 적용된다** — 세 섹션 이름이 있는지는 어떤 논문이 왔는지와 무관하다.

측정 전에 §5.2 를 개정하고 사유를 적었다. 조건 둘을 지킨다:
1. 모델별 `rag_ctx_chars` 분포를 결론에 같이 적는다. **모델 간에 치우쳐 있으면 판정에 쓰지 않는다.**
2. 내용 정확성은 재지 않는다.

근거: [`../checkpoint_1004/04_eval/`](../checkpoint_1004/04_eval/) 7모델 168시행에서 ctx 중앙값이 2478~2605 로 모여 있고 8문항 중 3개는 21시행 전부 동일했는데, 이탈은 3/24~23/24 로 벌어진다.

## 3. 저장 지점

`SAVE_STEPS=3` · `SAVE_STEPS_MAX=24` → **3 · 6 · 9 · 12 · 15 · 18 · 21 · 24** 스텝.

- **`max_steps` 를 자르지 않는다.** 자르면 선형 감쇠 스케줄의 총 길이가 바뀌어 lr 궤적이 v9 과 달라진다. 138스텝을 끝까지 돌리고 초반만 올린다 (`SAVE_STEPS_MAX` 가 업로드만 거른다 — 학습·디스크 저장은 그대로).
- 3스텝 = 예시 24건. 그보다 촘촘히 가면 체크포인트가 46개가 되고 머지·측정이 감당이 안 된다. **step 3 에서 이미 무너져 있으면 그것이 답이다** ("거의 즉시").

## 4. 가설

- **H1 (점진)**: 이탈 수가 3 → 24 스텝에 걸쳐 단조 증가한다. base 3/24 에서 시작해 ckpt23 의 19/24 로 간다.
- **H2 (급변)**: 어느 한 지점에서 계단처럼 뛴다 (예: step 6 에서 4/24, step 9 에서 17/24).
- **H3 (즉시)**: step 3 에서 이미 15/24 이상이다. 24건의 예시만으로 템플릿을 버린다는 뜻이고, 그러면 **이 구간도 너무 거칠다** — 더 촘촘한 저장이 필요하다고 적는다.

셋 다 운영에 다른 함의를 준다. H3 면 "조금만 학습해도 시스템 프롬프트 준수를 잃는다" 이고, 그것이 가장 나쁜 소식이다.

## 5. 판정 (사전 선언 — 결과를 본 뒤 바꾸지 않는다)

**주 지표**: RAG 8문항 × 3회 = 24시행에서 **템플릿 이탈 수** — 응답에 `선별 논문`·`부족 논문`·`Research Gap` 중 **하나도 없는** 시행의 개수. 마크업(`##`·`###`·굵게)과 무관하게 **섹션 이름**으로 센다 ([`../length_mechanism_1003/count_sections.py`](../length_mechanism_1003/count_sections.py) 와 같은 정의).

**모델**: 체크포인트 8개 + **base**(3/24 예상) + **v9**(23/24, 이 설정의 끝점) + **v10**(7/24, 대조) = **11개**, 같은 세션.

### 5.0 전제 점검 (문지기)

같은 밤에 **base 가 낮고 v9 이 높아야** 이 지표가 작동하는 것이다.

- **통과**: base 이탈 ≤ 8/24 **and** v9 이탈 ≥ 16/24.
- **실패 → 판정 불가.** 지표가 그 밤에 작동하지 않았다는 뜻이고, 체크포인트 수치를 읽지 않는다. (base 3/24 · v9 23/24 는 두 세션에서 재현됐으므로 이 문턱은 여유가 있다: 10-03 base 4·v9 23, 10-06 base 3·v9 23.)

### 5.1 주 판정 — 무너지는 지점

**정의**: 이탈 수가 처음으로 **12/24(절반) 이상**이 되는 스텝을 **붕괴 지점**이라 부른다. 절반을 쓰는 이유는 base(3/24)와 v9(23/24)의 중간이고, 3회 다수결이 아니라 **시행 수**를 세므로 문턱이 하나 필요하기 때문이다.

| 관측 | 판정 |
|---|---|
| 붕괴 지점이 **6~24 사이**에 있고 그 앞 단계들이 8/24 미만 | **H2 (급변)** — 그 지점을 결론에 적는다 |
| 이탈 수가 단조 증가하며 중간 단계들이 8~16 구간을 지난다 | **H1 (점진)** |
| **step 3 이 이미 ≥ 12/24** | **H3 (즉시)** — 이 해상도로는 못 가른다고 적고, 더 촘촘한 저장을 다음 라운드로 넘긴다 |
| 24스텝까지 전부 < 12/24 | **판정 불가** — ckpt23(19/24)과 어긋난다. 학습 간 변동을 먼저 의심하고 ckpt138 과 맞대어 본다 |

**단조성을 요구하지 않는다.** 24시행짜리 카운트는 흔들린다. 그래서 "붕괴 지점" 을 단일 문턱 통과로 정의하고, 비단조가 나오면 그 사실을 적는다.

### 5.2 같이 보는 것 (판정 아님 — 기록만)

- 모델별 `rag_ctx_chars` 중앙값·범위 (§2 의 조건 1 — **이것이 치우치면 판정 자체를 버린다**).
- 고정 슬롯당 값 길이 (템플릿을 따른 시행에서만).
- 응답 전체 길이 중앙값 — 길이 규범이 이 구간에서 함께 움직이는지. [`../checkpoint_1004/`](../checkpoint_1004/) 는 길이 **제약 준수**가 안 움직인다고 했지만 **출력 길이** 자체는 별개 지표다.
- 이 라운드는 **RAG 슬롯만** 잰다(`SLOTS=rag`). 다른 슬롯 실패율을 전체 라운드와 맞대지 않는다.
