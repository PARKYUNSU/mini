## 3. 참고 (판정 아님)

- **계획 길이 40문항 전체**(`planner_09-48`): base:v10 **12:3, p=0.035** · v9:v10 **12:1, p=0.003** — 둘 다 같은 방향으로 유의하다. 바닥 문항이 섞여 있어 판정에는 쓰지 않는다.
- **`must_exclude` 16문항**(`planner_49-64`): base:v10 2:2(불일치 4) · v9:v10 1:1(불일치 2) — 둘 다 판정 불가. **효과는 여전히 길이 제약에 특정된다.**
- **최장 단계줄 중앙값**: v10 **38.0** · base 42.0 · v9 44.0 (n=192/188/168). §3 의 기전("v10 이 단계 줄을 짧게 쓴다")과 일치한다.

### 측정 버그를 하나 고쳤다

처음 집계에서 base 의 표본이 **26/192** 로 나왔다. 원인은 **base 가 `1 단계:` 처럼 숫자와 단계 사이에 공백을 넣고 v9/v10 은 붙여 쓰는 것**인데, 내 정규식이 공백을 허용하지 않았다. 고치니 **168/192** 가 됐고 위 수치는 고친 뒤의 것이다. **주 판정은 영향받지 않는다** — 그쪽은 `constraint_check` 의 `max_chars_per_line` 을 쓰고 이 정규식을 쓰지 않는다.

이 차이 자체도 기록해 둔다: 같은 지시(`첫 줄은 반드시 '1단계:'로 시작한다`)에 base 는 공백을 넣고 파인튜닝 모델은 붙여 쓴다.

## 4. 채택한다면 — 배선은 §2 대로

[`README.md`](README.md) §2 에 측정 전에 적어 둔 제약을 다시 확인한다. **`LOCAL_LLM_MODEL` 을 바꾸는 것은 채택 경로가 아니다** — `get_planner_llm` 을 잡담·라우터 폴백·**코딩 폴백**(`executor_node`)이 공유하고 v10 은 코딩이 더 나쁘다. 채택은 `get_planner_plan_llm` 전용 환경변수로 한다.
