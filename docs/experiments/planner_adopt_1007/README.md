# v10 을 계획 슬롯에 채택할 것인가 (사전 등록)

- 시작일: 2026-10-07
- 선행: [`../protocol.md`](../protocol.md) §3 (여섯 세션 재현 + 한계 (1)) · [`../planner_signal_0929/`](../planner_signal_0929/) · [`../checkpoint_1004/05_conclusion.md`](../checkpoint_1004/05_conclusion.md) §6 (사후 탐색)
- **새 모델을 만들지 않는다.** 이미 있는 `yunsur_v10`·`yunsur_v9`·base 를 다시 잰다.
- 비용: 학습 0 · 측정 1회(**계획 슬롯만**, 3모델 ≈ 60분)

## 1. 왜 이것이 남은 유일한 결정 질문인가

운영은 계획 슬롯에 **base** 를 쓴다. 아홉 라운드의 실질 성과는 "RAG 에 v9, 나머지는 건드리지 않는다" 하나이고, v10·v11 은 채택되지 않았다.

그런데 [`../protocol.md`](../protocol.md) §3 이 확립한 것은 **v10 이 계획 길이 제약에서 v9 보다 낫다**(여섯 세션)이고, 같은 절의 한계 (1)이 이렇게 적혀 있다 — **"base 대비로는 유의하지 않다 (p=0.065 · 0.125) … 운영의 계획 슬롯은 base 를 쓰므로 교체 근거로는 부족하다."**

**그 한계가 흔들렸다.** [`../checkpoint_1004/`](../checkpoint_1004/) 에서 사후 탐색으로 **base vs v10 = 8:0, p=0.008** 이 나왔다. 사전 등록하지 않았으므로 §3 을 갱신하지 않고 "다음 라운드에 사전 등록해 묻는다" 고 적었다. 이 라운드가 그것이다.

세 세션의 base : v10 (전부 v10 쪽):

| 세션 | 결과 | p |
|---|---|---|
| [`planner_signal_0929/`](../planner_signal_0929/) | 9 : 2 | 0.065 |
| 같은 라운드 복제 | — | 0.125 |
| [`checkpoint_1004/`](../checkpoint_1004/) (**사후**) | 8 : 0 | **0.008** |

**방향은 세 번 다 같고 둘은 검정력 부족, 하나는 유의하다.** 사전 등록해 다시 물을 값이 충분하다.

## 2. 채택이 건드리는 것 — 배선 제약을 먼저 적는다

`get_planner_llm` 과 `get_planner_plan_llm` 은 **둘 다 모델 인자 없이** 기본값(`LOCAL_LLM_MODEL` = base)을 쓴다. 그래서 **`LOCAL_LLM_MODEL` 을 바꾸는 것은 채택 경로가 아니다**:

| 슬롯 / 경로 | getter | v10 으로 바뀌면 |
|---|---|---|
| **계획 (Planner)** | `get_planner_plan_llm` | ← **여기만** 바꿔야 한다 |
| 잡담 (Direct Answer A) | `get_planner_llm` | 건드리지 않는다 |
| 라우터 Ollama 폴백 | `get_planner_llm` | 건드리지 않는다 |
| **코딩 폴백** (`executor_node`) | `get_planner_llm` | **v10 은 코딩이 더 나쁘다** (§3 한계 (2): 30.0% vs v9 18.9%, 이번 ckpt 라운드 28.9% vs base 20.0%) |

즉 채택은 **`get_planner_plan_llm` 에만 적용되는 새 환경변수**(예 `PLANNER_PLAN_MODEL`)로 해야 한다. 기본값을 바꾸면 Groq 이 끊겼을 때의 코딩 품질이 같이 나빠진다 — [`../prior_work.md`](../prior_work.md) §6 이 배선한 폴백의 의미가 깎인다.

**이 제약은 측정 결과와 무관하게 성립한다.** 그래서 먼저 적는다.

## 3. 측정

[`scripts/eval_multi_round.sh`](../../../scripts/eval_multi_round.sh) 로 **base · v10 · v9** 를 같은 세션에서, **계획 슬롯만**:

```bash
SLOTS=planner nohup caffeinate -i bash scripts/eval_multi_round.sh adopt yunsur_v10 yunsur_v9 > .cron/eval_adopt.log 2>&1 &
```

**계획 슬롯만 재는 것이 정당한 이유**: §2 의 배선 제약대로 채택은 `get_planner_plan_llm` 에만 적용되고, 평가기의 `planner` 슬롯이 바로 그 getter 에 대응한다([`tests/unit/test_eval_num_predict_matches_prod.py`](../../../tests/unit/test_eval_num_predict_matches_prod.py) 의 `SLOT_TO_GETTER`). 잡담·코딩·RAG 는 이 결정으로 바뀌지 않으므로 잴 필요가 없다. 대신 **다른 슬롯 실패율을 전체 라운드와 맞대지 않는다** (§5.2 의 슬롯 제한 경고).

**주 지표**: `planner_33`~`48` **16문항**, 3회 다수결 — §3 이 확립한 것과 **같은 자**다. 바꾸지 않는다.

## 4. 판정 (사전 선언 — 결과를 본 뒤 바꾸지 않는다)

### 4.0 문지기

**v9 vs v10 이 재현되어야 해석한다** — 일곱 번째다. 주 지표에서 불일치가 v10 쪽으로 쏠리고 McNemar **p < 0.05**. 깨지면 **판정 불가**로 적고 "일곱 번째 세션에서 재현이 깨졌다" 를 결과로 남긴다.

### 4.1 주 판정 — base vs v10

주 지표 16문항 · 짝지은 McNemar 정확검정 · α = 0.05 · 단일 검정(보정 없음).

| 결과 | 판정 |
|---|---|
| 불일치가 v10 쪽으로 쏠리고 **p < 0.05** | **이번 세션 유의** → §4.2 의 채택 규칙으로 |
| p ≥ 0.05 이고 불일치 **6쌍 이상** | **차이를 보이지 못했다** — §3 의 한계 (1)을 유지한다 |
| 불일치 **6쌍 미만** | **판정 불가** ([`../protocol.md`](../protocol.md) §2.3). "차이 없음" 으로 읽지 않는다 |

### 4.2 채택 규칙 — **한 세션으로는 바꾸지 않는다**

운영 슬롯을 바꾸는 결정이므로 단일 세션을 근거로 삼지 않는다. §3 의 결론 자체가 여섯 세션 재현으로 세워졌고, 같은 기준을 적용한다.

- **채택**: **독립된 두 세션**(다른 밤)에서 base vs v10 이 **둘 다 p < 0.05** 이고 방향이 v10 쪽.
- **보류**: 한 세션만 유의하거나 방향이 갈리면 **채택하지 않고** 그 사실을 §3 한계 (1)에 수치와 함께 적는다.
- 채택 시 배선은 §2 대로 `get_planner_plan_llm` 전용 환경변수로 한다. **`LOCAL_LLM_MODEL` 을 바꾸지 않는다.**

이 라운드는 **세션 1**이다. 유의하게 나와도 세션 2 전에는 운영을 바꾸지 않는다.

### 4.3 같이 보는 것 (판정 아님 — 기록만)

- **base vs v9**: §3 은 이 효과가 **lr 축에서만** 나온다고 적었다(base:v9 는 3:4, p=1.000). 이 세션에서도 null 이어야 한다. **v9 쪽으로 유의하게 나오면** §3 의 귀속이 흔들리므로 그 사실을 적는다.
- 계획 길이 40문항 전체(`planner_09-48`)와 `must_exclude` 16문항(`planner_49-64`). 바닥 문항이 섞여 있어 판정에 쓰지 않는다.
- 계획 슬롯 실패율과 Wilson 구간 · 최장 단계줄 길이 중앙값(§3 의 기전 지표).
