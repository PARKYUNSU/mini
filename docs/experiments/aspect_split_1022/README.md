# 조건이 여러 개인 질문은 조건마다 따로 검색 — 사전 등록 (2026-10-22)

> 측정 **전에** 쓴다. 출발점: 실제 사용(10-22 18:26 "RAG 에서 검색된 문서의 **순서나 개수**가 답변 품질에 주는 영향 …") 외부 리뷰 — Lost in the Middle(순서) · Long-Context LLMs Meet RAG(개수)가 빠짐. 둘 다 DB 에 있고, 조건 하나씩 검색하면 1위로 나온다(paper_blocks_1022 진단). 검색어 하나(`retrieval order impact answer quality rag study number of retrieved documents effect`)에 두 조건을 섞어 둘 다 밀렸다. paper_blocks_1022 는 칸을 늘려도 효과가 없었다 — 칸이 아니라 검색어 문제.

## 1. 바꾸는 것 — `RAG_ASPECT_SPLIT` (기본 `0`)

`1` 이면 RAG 답변 경로에서(비교 질문 · 이어지는 질문 재사용이 아닐 때) 질문에 나열 표지(`…나 / 이나 / 또는 / 혹은 / 및 / 랑 / 이랑 / 와 / 과` + 공백)가 있으면:
- 보조 LLM(`get_rag_query_rewrite_llm`, 비교 분리와 같은 것)에 "질문이 or/and 로 이은 **서로 다른 조건**을 묻는가? 그렇다면 조건마다 공통 주제를 포함한 짧은 영어 학술 검색어를 한 줄씩(2~3줄), 그 조건에 연구자들이 쓰는 표준 용어가 있으면 그것으로; 조건이 하나면 NONE".
- 조건마다 검색(비교 분리와 같은 설정)해 각 상위 2블록을 원래 검색 블록 앞에 합친다(`_merge_rag_blocks`, 같은 논문 한 번). 이후 top-5 · 관련 문서 거르기 등은 그대로.
- 프롬프트에 **구체적 용어 예시를 넣지 않는다**(query_extract_1021: 예시 용어가 무관한 질문에 새어 들어 기각).
- 코드 `core/graph/agent_nodes.py` `_extract_aspects`, 테스트 `tests/unit/test_aspect_split.py`.

## 2. 방법 — 답 재생성 (맥미니)

- **조건 세트 12문항(새로 만듦):** `questions.tsv` · `aspects.json`(문항마다 조건 2개 × 조건별 정답 논문 — DB 제목에서 골랐다, gold 는 조건별로 완전하지 않다) · `gold.jsonl`(조건 합집합).
- **보호 세트:** real40 + real2 74문항.
- 대조 `as0` · 처리 `as1`, 운영 `.env` 그대로, `--answer --save-context`. 실행 `.cron/run_as.sh`, 채점 `score.py`.

## 3. 판정 (측정 전 고정)

| 지표 | 기준 |
|---|---|
| **주:** 조건 세트 12문항 × 조건 2 = 24 조건 중, **컨텍스트(답변 모델에 간 것)에 그 조건의 정답 논문이 1편 이상** 있는 조건 수 | 처리 > 대조, 조건 짝 McNemar 양측 p < 0.05 · 처리 ≥ 18/24 |
| 보조: 같은 24 조건 중 **답이 인용한** 조건 수 | 처리 ≥ 대조 |
| 보호: 74문항 검색 ok · N 정답 · C 두 편 · T 정답 인용 ≥ 3 | 각각 처리가 대조보다 2 이상 낮지 않음 |
| 보호: 응답 시간 중앙(74) | ≤ 대조 + 5s · 조건 세트는 보고 |
| 보고: 분리가 걸린 문항 수(12 중 · 74 중)와 뽑힌 검색어, 12문항 답 직접 읽기(조건별로 다루는지) | |

채택이면 사용자 승인 후 운영 `.env` `RAG_ASPECT_SPLIT=1` + 봇 재시작.

예상: 대조 조건 커버 10~14/24 → 처리 18~22/24. 74문항 중 분리가 걸리는 것은 0~5.
