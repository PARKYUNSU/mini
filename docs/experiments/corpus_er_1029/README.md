> 측정 **전에** 쓴다. 출발점: 실사용 job 134 · 135(10-28 · 29, "두 DB 에서 비슷하거나 같은 내용을 찾는 연구") — 판정 `없음`. `probe.py`(분야 용어 영어 검색어 8개, 읽기만)로 보니 DB 에 **개체 매칭(entity resolution) · 레코드 연결 · 대규모 근접 중복 탐지 · 학습 데이터 중복 제거 · 유사도 조인** 핵심 논문이 없다(상위 10 이 지식 그래프 완성 · Text-to-SQL · 문서 파싱 등). 스키마 · 온톨로지 매칭과 지식 그래프 개체 정렬은 일부 있음(OntoAligner 2503.21902 · LLM-Align 2412.04690 등).
> 앞 두 라운드에서 배운 것: corpus_seed_1020 — 질문 단위로 5편씩 고르면 그 질문에는 듣지만 같은 분야 새 질문(held-out)에는 약했다(15 → 17). corpus_seed_1023 — 넣은 논문이 실제 질문 검색어로는 안 찾혔다(1/4). 그래서 이번엔 **분야 단위**로 고르고, **후보 찾기에 쓰지 않은 일상어 질문**으로만 잰다.
> orx 사용: 승인된 용도(`ops/openresearch_policy.md` "코퍼스 수집 후보 찾기") — 목록만 만들고 수집은 우리 파이프라인.

## 1. 바꾸는 것 — 코퍼스에 논문 추가 (코드 · 설정 변경 없음)

**후보 규칙 (측정 전 고정, 손으로 고르지 않는다)**
- 분야 검색어 6개(`topics.tsv` T1–T6, 평가 질문과 따로 씀)마다 `orx discover embedding "<검색어>"` 를 `--prioritize popular --limit 10` 과 기본 정렬 `--limit 10` 두 번.
- 순서: popular → 기본, 중복 제거, **이미 DB 에 있는 논문 제외**, arXiv ID 만, 분야당 앞에서 **8편**. 상한 48편. 원본 `raw/`, 목록 `candidates.json` · `candidates.yaml`.

**수집**: `apps.backfill.ingest_classics --yaml candidates.yaml`(매일 수집과 같은 경로, 운영 Chroma 서버 + 쓰기 잠금) → 임베딩 캐시 재생성(`scripts/build_emb_cache.py`) → 봇 재시작. 받지 못한 논문은 기록만.

## 2. 측정 — 검색만(`--save-context`, 답변 없이, 운영 경로), 수집 전 `ce0_*` · 후 `ce1_*`

- 대상 12문항 `questions.tsv`(E01–E11 일상어 질문 — 이 사전 등록과 함께 먼저 씀, 후보 찾기에 쓰지 않음 — + 실사용 R_134). gold 없음.
- 보호: 162 · real40 · real2.
- **관련성 판정**: 두 조건 컨텍스트의 (질문, 논문) 쌍을 섞어 조건을 모른 채 제목 + 초록으로 0 · 1 · 2(2 = 질문을 직접 다룸).

## 3. 판정 (측정 전 고정)

| 지표 | 기준 |
|---|---|
| **주:** 대상 12 — 질문별 컨텍스트 '2' 논문 수 | 후 > 전, 부호 검정(동점 제외) 양측 p < 0.05 |
| 부: 대상 12 — '2' 논문이 1편 이상인 질문 수 | 보고 |
| 보호: 검색 ok 162 · real40 · real2 | 각 세트 후가 전보다 3 이상 낮지 않음 |
| 보호: 대상 12 '0' 합 | 후 ≤ 전 × 1.5 |
| 보고: 후보 수 · 수집 성공 · 실패 · 수집 논문이 대상 컨텍스트에 든 자리(그중 '2') · `probe.py` 분야 용어 검색어로 찾히는 수집 논문 수 | |

채택이면 수집분을 그대로 둔다. 기각이면 수집분을 지울지 사용자와 정한다.

예상: 12문항이라 p < 0.05 에는 늘어남 : 줄어듦이 9 : 0 이상 필요 — 빡빡하다. corpus_seed_1023 처럼 색인은 되는데 9B 검색어가 분야 용어를 못 만들어 안 찾힐 수 있다(그러면 `probe.py` 에서는 찾히고 대상 질문에서는 안 찾히는 모양 — 병목이 검색어라는 증거, 2번 후보 "큰 모델 검색어"의 근거가 된다).
