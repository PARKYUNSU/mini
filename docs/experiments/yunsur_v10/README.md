## 1. 왜 lr 인가

[`../prior_work.md`](../prior_work.md) §4 에 적은 우리 설계의 맹점이다. **lr 을 v3 부터 v9 까지 2e-4 로 의도적으로 고정했다.** "데이터만 바꾼 효과를 분리한다" 는 정당한 이유였지만, 그 결과 **문헌이 주 레버로 지목하는 하이퍼파라미터를 다섯 라운드 동안 한 번도 시험하지 않았다.**

근거 문헌은 [`SFT Doesn't Always Hurt General Capabilities`](https://arxiv.org/html/2509.20758v3) — **학습률을 낮추면 도메인 성능과 일반 능력 보존을 동시에 얻는 절충점이 생긴다**는 주장이다.

### 과장하지 않기 위해 적어 둔다

논문의 권고 lr **1e-6 은 full fine-tuning 기준**이고, LoRA 는 관례적으로 훨씬 높은 lr 을 쓴다 (2e-4 는 LoRA 표준 기본값에 해당). **"우리가 200배 높다" 는 서술은 성립하지 않는다.** 직접 비교 가능한 LoRA 기준 권고치는 조사에서 찾지 못했다 (§4).

그래서 **1e-6 을 그대로 쓰지 않고 5e-5(1/4)를 쓴다.** LoRA 범위 안에서 한 단계 낮추는 보수적인 값이다. 이 라운드가 재는 것은 "논문 값의 재현" 이 아니라 **"우리가 한 번도 움직이지 않은 축이 움직이는가"** 다.

### 이번 라운드가 겨냥하는 잔여 격차

v9 는 세 운영 슬롯(잡담·계획·RAG)에서 base 와 짝지은 불일치 **0개**로 이미 동률이다. 남은 것은 코딩 슬롯의 잔여 격차뿐이다 — v9 코딩 실패율 **21.1%**, base **15.6%**, v9 만 실패한 문항 1개(p=1.000). v9 데이터에는 코딩이 **한 건도 없으므로** 이 격차는 학습 대상이 아닌 능력의 **망각**으로 볼 수 있다. lr 을 낮추면 망각이 줄어든다는 것이 문헌의 주장이고, 그렇다면 여기서 드러나야 한다.

## 2. 가설

먼저 **이 라운드가 답할 수 없는 것**을 적어 둔다. v9 가 측정의 천장에 닿아 있다
([`../yunsur_v9/05_conclusion.md`](../yunsur_v9/05_conclusion.md)):

| 슬롯 | v9 만 실패 | 불일치 쌍 | McNemar p |
|---|---|---|---|
| 잡담·계획·RAG | **각 0개** (base 는 각 1개) | 0 | 1.000 |
| 코딩 | 1개 | 2 (방향 대칭) | 1.000 |

세 슬롯은 0 아래로 내려갈 수 없고, 코딩은 v9 데이터에 한 건도 없으므로 학습이
**깎을 수만 있다** — 최선이 "base 와 같음" 인데 이미 p=1.000 이다. 게다가
[`../protocol.md`](../protocol.md) §2.3 이 말하듯 불일치 쌍이 6개는 한쪽으로
쏠려야 p<0.05 인데, v9 대 base 는 2쌍이었다. 코딩 21.1% [14.0, 30.6] 과 base
15.6% [9.5, 24.4] 는 구간이 거의 포개진다.

**그러므로 이 라운드는 열화를 탐지할 수 있을 뿐, 개선을 유의하게 보일 수 없다.**
개선 방향을 판정에 넣지 않는 이유이고, 헤드룸이 필요하면 문항을 어렵게 만들어야
하는데 그것은 §2.2 에 따라 base·v6·v9 전부를 다시 재는 별도 결정이다.

- **H1 (주): 세 운영 슬롯은 나빠지지 않는다.** 잡담·계획·RAG 에서 v10 만 실패한 문항이 슬롯 전체 합쳐 1개 이하. lr 을 낮춘 대가로 학습이 부족해지면 여기서 먼저 깨진다.
- **H2 (반대 위험): 138 스텝 · lr 1/4 는 학습이 모자랄 수 있다.** RAG 슬롯에서 v6 가 고쳤던 literal `\n` 같은 형식 학습이 되돌아오면 과소적합의 신호다. **H1 과 H2 는 같은 실패를 양쪽에서 본다.**
- **H3 (탐색 — 판정에 쓰지 않는다): 코딩 잔여 격차가 줄어든다.** v9 코딩 21.1% 는 학습 대상이 아닌 능력의 망각으로 볼 수 있고, lr 을 낮추면 망각이 준다는 것이 문헌의 주장이다. 다만 위에서 적었듯 **유의하게 보일 수 없으므로** 방향만 기록한다.

## 3. 판정 (사전 선언 — 결과를 본 뒤 바꾸지 않는다)

[`scripts/eval_round.sh`](../../../scripts/eval_round.sh) `yunsur_v10` 으로 v10 과 base 를 같은 세션에서 재고 짝지어 비교한다 (54문항 × 3회, sha256 `a94d4708f9b6`, v9 기준 약 121분).

이 라운드가 묻는 것은 하나다 — **lr 을 1/4 로 낮춰도 v9 의 결과가 유지되는가.** 개선이 아니라 **비열등성**을 판정한다.

- **통과 → lr 5e-5 가 v9 를 유지한다**: 잡담·계획·RAG 에서 v10 만 실패한 문항이 **합쳐 1개 이하** **and** 코딩에서 base 대비 McNemar **p ≥ 0.05** (유의한 열화 없음).
  통과는 "lr 인하가 이 규모에서 해롭지 않다" 는 뜻이지 **개선의 근거가 아니다.** 운영 교체 여부는 이 판정과 별개로 정한다 — v9 대비 우위가 측정되지 않으므로, 바꿀 이유가 따로 없으면 **v9 를 유지하는 것이 기본값**이다.
- **실패 → v9 유지, lr 인하 폐기**: 잡담·계획·RAG 에서 v10 만 실패한 문항이 **2개 이상**, 또는 코딩에서 base 대비 **p < 0.05**. 과소적합으로 해석한다.

**참고 지표 (판정 아님, 기록만).** 코딩 시행 실패율과 Wilson 95% 구간, `timeout` 건수, loss 궤적을 v9·base 와 나란히 적는다 (v9 21.1% [14.0, 30.6] · timeout 13, base 15.6% [9.5, 24.4] · timeout 5). 방향은 남기되 **결론으로 쓰지 않는다** — §2.3 의 "단일 측정값을 다음 라운드의 판정 문턱으로 고정하지 않는다" 를 지킨다. 이 노트의 초안이 실제로 그 금지를 어겼다가(코딩 실패율 21.1% 미만을 통과 조건에 넣었다) 착수 전에 고쳤다.

코딩 슬롯은 운영이 쓰지 않는다 (Executor 는 Groq). 다만 2026-09-27 에 `executor_node` 에 **로컬 base 폴백**이 배선됐으므로 ([`../prior_work.md`](../prior_work.md) §6), 이제 "Groq 이 끊겼을 때의 품질" 이라는 실제 의미를 갖는다 — 열화 감시 대상으로는 유효하다.

부수 비교로 v10 vs v9 도 본다 ([`scripts/eval_pairwise.py`](../../../scripts/eval_pairwise.py)). **다른 밤의 측정이므로** 판정에 쓰지 않고 방향 확인에만 쓴다.

## 4. 학습

v9 와 동일. [`scripts/runpod_train.sh`](../../../scripts/runpod_train.sh) (L40S 48GB · 볼륨 50GB · 컨테이너 디스크 60GB) → HF private → 맥미니 `merge_lora_gguf.sh v10`.

`VERSION=v10`, `HF_REPO=YUNSU24/yunsur_v10_lora`, 데이터는 v9 것을 그대로 지정. **`KEEP_POD` 은 켜지 않는다** (v5 에서 컨테이너 재시작 루프를 만들었다).

**lr 은 소스를 고쳐 박지 말고 환경변수로 준다.** [`scripts/train_lora.py`](../../../scripts/train_lora.py) `HPARAMS["learning_rate"]` 를 `LEARNING_RATE` 로 덮어쓸 수 있게 바꾸고 기본값은 2e-4 로 둔다 — 그래야 v9 재현이 깨지지 않고, 이 라운드의 변경이 명령줄에 남는다.
