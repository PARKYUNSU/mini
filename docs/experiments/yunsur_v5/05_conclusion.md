### 코딩이 나빠진 진짜 이유 — 주석이 아니라 자기 수정 서술

v4의 진단은 "코드 안 긴 한국어 주석 → 토큰 상한(800)에서 잘림"이었고, v5는 그에 맞춰 **주석 비율 >30% 거절** 필터를 넣었다. 필터 자체는 데이터에서 작동했다 (코딩 주석 비율 p95 0.42 → 0.16, 학습 토큰 잘림 0건). 그런데 실패는 그대로 남았다.

실제 실패 원문(`04_eval_v5/yunsur_v5.jsonl`)을 보면 양상이 다르다.

```
fibonacci = [0, 1]
while len(fibonacci) < 10:
    fibonacci.append(sum(fibonacci[-2:]) if len(fibonacci) >= 2 else None # 단순화 로직 수정 필요 없음 (다음 코드 참조)

# 올바른 구현으로 재작성 및 출력합니다.

def generate_fibo(n):
    fib = [0, 1] * n + []
```

구현을 한 번 쓴 뒤 **주석으로 자기 코드를 의심하고**("로직 수정 필요 시 재작성 가능하지만", "더 간결하고 정확한 방식 적용 후 출력합니다"), **두 번째 구현을 시작한다.** 그러다 토큰 상한에 걸려 표현식 중간에서 잘리고 `syntax` 또는 펜스 미닫힘이 된다. 이 문항들의 응답 시간은 51~53초로, v5 코딩 중앙값 3.3초와 완전히 다른 꼬리다.

같은 패턴이 v4 머지의 `coding_04`·`coding_06`에도 그대로 있다 (96~99초). 즉 **v5가 새로 만든 습관이 아니라 베이스에서 온 행동**이고, v5는 그것을 `coding_06`에서 더 자주 발동시켰을 뿐이다.

주석 비율 필터가 빗나간 이유는 분명하다. 그 필터는 **채택된 샘플 안의 주석 양**을 재는데, 문제는 **생성 시점에 모델이 답을 두 번 쓰는 행동**이다. 주석은 그 행동의 흔적이지 원인이 아니었다.

한편 v5의 코딩 중앙값은 5.7s → 3.3s로 짧아졌다. 보통의 코딩 답변은 실제로 짧고 빨라졌고, 실패는 자기 수정이 발동하는 꼬리에만 남았다.

### 이 결론이 기대는 표본

코딩 n=18은 6문항 × 3회다. v5의 코딩 실패 4건은 **2문항**에서 나왔고, 그중 `coding_06`이 3/3으로 전부 실패했다. strict 차이 +5.5%p는 18건 중 1건 차이라 경계선이지만, hard만 보면 3건 대 1건(+11.1%p)으로 방향이 같고 `coding_06`은 3회 모두 재현됐다. 노이즈로 보기는 어렵되, **"코딩이 전반적으로 나빠졌다"가 아니라 "한 유형에서 재현성 있게 실패한다"** 로 읽는 것이 정확하다. 코딩 문항 수를 늘리지 않으면 이 구분을 더 좁힐 수 없다.

## 운영 결정

- **운영 로컬 모델은 base `qwen3.5:9b` 유지** (전체 1%). v5로 바꿀 근거 없음.
- **RAG 답변 슬롯은 v4 → v5로 교체 가능.** 둘 다 0%로 동률이고 속도도 같지만(32.9s vs 33.2s), v5는 플래너·잡담에서도 v4보다 낫거나 같아 슬롯을 넓힐 여지가 있다. 다만 **동률을 이유로 바꾸는 것이므로 서둘 필요는 없다** — 현행 `RAG_ANSWER_MODEL=yunsur_v4` 유지도 동등하게 정당하다.
- **코딩 슬롯은 계속 base.** 파인튜닝 4종 모두 base(0%)보다 나쁘다.
- **플래너 슬롯은 재검토 가치가 생겼다.** v5 4.2% vs base 0% — 차이가 1건으로 좁혀졌다. 다음 라운드에서 이 슬롯만 넘어설 가능성이 있다.

## 다음 라운드(v6)에 반영할 것

1. **코딩은 "한 번에 하나의 구현" 을 학습시킨다.** 주석 비율이 아니라 **코드 블록이 2개 이상이거나 "재작성·수정·또는 다음과 같이" 류의 자기 수정 표현이 있는 샘플을 거절**한다. v5 필터는 증상을 쟀다.
2. **코딩 평가 문항을 6 → 12문항으로 늘린다.** 지금 표본으로는 "한 문항의 재현성 있는 실패"와 "슬롯 전반의 악화"를 구분할 수 없다.
3. 플래너는 `planner_08`(FastAPI 류 서버 기동) 같은 **실행 환경 준비가 섞인 요청** 시드를 보강한다. 남은 1건이 이 유형이다.
4. RAG 400건·잡담 300건은 유지 — 2라운드 연속 효과 확인.
5. 하이퍼파라미터는 계속 고정. v4→v5에서 데이터만 바꿔 플래너가 16.7%→4.2%로 움직인 것이 데이터 효과의 크기를 보여준다.

## 실험 과정에서 얻은 교훈 (실패 기록)

- **원인 진단은 데이터가 아니라 실패 원문에서 나와야 한다.** v5 코딩 필터는 v4 실패의 *요약*(주석이 길더라)에서 나왔고, 원문의 *행동*(답을 두 번 쓴다)을 보지 않았다. 필터는 데이터 지표를 개선했지만 실패율은 못 줄였다.
- **RunPod 이미지 핀은 썩는다.** v4의 `runpod/pytorch:2.4.0-py3.11-cuda12.4.1` 은 한 달 만에 레지스트리에서 사라졌고 cu124 이미지 자체가 없어졌다. 실제 학습은 cu128/torch 2.8 에서 돌았다.
- **학습 라이브러리 API도 썩는다.** TRL 이 `SFTTrainer(tokenizer=)` → `processing_class=`, `max_seq_length` → `max_length` 로 바뀌어 학습 직전에 죽었다. 버전 핀 대신 `inspect.signature` 로 맞췄다 (`53f6d69`).
- **`KEEP_POD=1` 로 정상 종료하면 RunPod 이 컨테이너를 재시작해 학습이 다시 돈다.** HF 어댑터가 덮어써지기 직전에 잡았다. 업로드 로그를 확인하면 즉시 terminate 할 것.
