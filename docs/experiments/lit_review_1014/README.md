# 문헌 조사 — 검색 순위·답변 활용 (OpenResearch `orx discover`, 2026-10-14)

> 도구: alphaXiv OpenResearch CLI `orx` 0.2.18 (맥미니 `~/orx/bin/orx`, 텔레메트리 끔, 셸 PATH 무변경). `orx discover embedding` 5회 · 각 12편 → 60편 중 관련 6편 초록 정독. 원본 JSON: [`raw/`](raw/).
> 출발점: 정답이 컨텍스트에 안 들어오는 문항 24/162 (15%), 서베이 질문 놓침, 9B 의 "덜 자세함"(upper_bound_1013, answer_detail_1013).

## 1. 지금 우리 검색 (코드 기준)

`core/rag/agent_chroma_rag.py`: 한국어 질문 → 검색어 확장(`query_expansion.build_multi_query_retrieval_queries`) → **BM25 + 벡터(all-MiniLM-L6-v2, 영어 전용) RRF 하이브리드** → 제목 인덱스 매칭 · 키워드 보충 → 논문 단위 가벼운 재순위 → 초록 800자 붙여 컨텍스트. MS MARCO cross-encoder 는 있지만 운영에서 건너뜀.

## 2. 읽은 것과 우리에게 주는 의미

| 논문 | 핵심 | 우리에게 |
|---|---|---|
| **HyPE** (2607.29402) Hypothetical Prompt Embeddings | 질문형 쿼리와 문서 문체 차이를 **색인 시점**에 해결 — 청크마다 가상 질문 여러 개를 미리 만들어 임베딩, 검색을 질문↔질문 매칭으로. 실행 시 지연 없음. 컨텍스트 정밀도 최대 +42%p, recall 최대 +45%p | **가장 직접적 후보.** 우리 질문은 전부 "~ 알려줘/있어?" 형 한국어. 청크 120만 개는 무리지만 **논문 단위(수집 JSONL 기준 초록 있는 논문 약 7천 편)** 로 가상 질문(한·영)을 만들면 하루 수집분만 추가 생성하면 된다. 9B 로 편당 수 초 |

## 3. 제안 (우선순위)

1. **논문 단위 HyPE 색인** (재학습 없음): 논문마다 초록에서 한국어·영어 가상 질문 3~5개 생성(9B 또는 Groq) → 별도 컬렉션 `paper_questions` → 기존 RRF 에 한 갈래로 추가. 측정: 162 + real_eval 40 의 정답 적중(짝 McNemar), 사전 등록 후. **주의:** 새 컬렉션 쓰기는 다른 쓰기 프로세스와 겹치지 않게(2026-10-14 사고).
2. **한국어 원문 → BGE-M3 갈래** 오프라인 측정: 검색어 확장 없이 원문 질문을 다국어 임베더로. 10-09 결과와 무엇이 달랐는지(입력이 한국어 원문인지) 먼저 확인.
3. **답변 활용은 학습 데이터로**: v15 후보 — 교사 데이터 본론에 "핵심 구성요소·결과" 명시, 초록 컨텍스트 붙은 운영 프롬프트로 재생성.

## 4. OpenResearch 써 본 느낌

- `orx discover` 는 **로그인 없이** alphaXiv 의미 검색 결과를 JSON 으로 준다 — 우리 봇의 arXiv 코퍼스 밖(최신 2026-09)까지 찾는다. 문헌 조사 용도로 충분히 쓸 만하다.
- 실험 트리(`orx exp`)는 "한 번 실행된 노드는 고치지 않는다 · 실행 명령은 고정, 코드만 바꾼다" 같은 규칙을 강제 — 우리 사전 등록 규칙과 같은 정신. 다만 프로젝트를 Git 저장소 단위로 관리하므로 지금 저장소에 붙이려면 따로 검토가 필요.
- 운영 DB·`.env` 와는 분리해서 썼다(`~/orx_lit`).

| **RINSE** (2609.37469) Relevance Is Not Sufficient Evidence | 충분성은 답을 만들기 전에 판정할 수 있지만 **단일 신호로는 안 된다** → (1) 질문의 모든 부분이 덮였나 (2) 답을 주는 발췌가 있나 (3) 작은 LM 이 발췌를 함께 읽고 판정 — 세 신호 결합 | 우리 판정은 (3) 하나뿐이고, "논문이 있나"와 "답(수치)이 발췌에 있나"를 섞는다. 수치 질문에서 논문은 있는데 수치가 발췌에 없으면 `없음` → 힌트가 **논문 자체를 부정**하게 만든다. **두 질문을 분리**해야 한다 |

| **ORDER** (2609.17012) 질의 조건부 라우팅 | 질문 군집마다 다른 검색 설정 | 장기 후보 — 질문 유형별 설정 |

### 제안 (우선순위)

1. **질문 유형 게이트 (규칙, 학습 없음):** 수치(`몇`, `%`, `얼마나`)·비교(`차이`, `비교`, `A랑/와 B`)·목록(`논문들`, `동향`, `정리`, `N개`)이면 판정·힌트를 건너뛴다. 근거: 2607.08456(선별 적용), 2608.02415(규칙성 분류 충분). 먼저 162 세트에서 게이트에 걸리는 문항·그중 정답 없음 수를 센다.
2. **판정을 두 질문으로 분리 (RINSE 식):** "질문이 가리키는 **논문**이 있나"(힌트 근거)와 "물은 **세부**가 발췌에 있나"(없으면 '수치는 발췌에 없음'을 말하게) — 후자는 논문 부정이 아니라 부분 답. v13 학습 형식과 다른 새 힌트가 필요해 1번 뒤에.
3. **검색 점수 분포 특징**(상위 거리 간격·분산·BM25/벡터 일치 등) + 판정을 합친 '없음' 결정 — 2609.11646. 오프라인으로 저장된 컨텍스트 거리만으로 잴 수 있다.
4. **비교 질문:** 질문 안의 방법 이름마다 제목 매칭 주입.
