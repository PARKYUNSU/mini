**배치 get 비용 분해** (논문 100편 묶음, 서로 다른 묶음):

- 필터(`$in`) 자체는 0.2s — 느린 건 **행 전부의 임베딩·메타데이터를 JSON 으로 주고받는 것**. 콜드/웜 차이가 아니다(반복이 더 느린 경우도 있음 — 서버 직렬화·파싱 부하로 추정, 메모리 여유 70%).
- 실제로 쓰는 건 논문당 가장 가까운 청크 3개(~300행)뿐.
- **기각한 대안:** 서버 `query(where=$in, n_results=전체 행)` 로 거리만 받기 — 1.3~13.9s 로 더 빠르지 않고, 근사(HNSW) 라서 112편 중 4편의 상위 청크가 현행과 다르다.
- 청크 ID 는 해시(예 `2f0364…`)라 논문 ID 로 계산할 수 없다 → 행이 어느 논문인지 알려면 메타데이터가 필요하다.

## 1. 가설

배치 get 을 **로컬 임베딩 캐시**(같은 임베딩, 같은 정확 코사인)로 바꾸면 검색 결과는 그대로이고, 비교 질문 지연이 크게 줄며 일반 질문도 줄어든다.

## 2. 바꾸는 것

1. **캐시 파일** `<CHROMA_DB_DIR>_emb_cache/`(운영: `/Volumes/T7 Shield/mini-chroma-rebuild2_emb_cache/`, 약 1.9GB fp32 + 인덱스 수십 MB):
   - `emb.f32` (memmap, 행 × 384) · `ids.npy` (청크 ID) · `paper_index.json` (정규화 paper_id → [시작, 끝) 행 범위, 논문별로 연속 배치) · `meta.json` (행 수·만든 시각·컬렉션 행 수).
   - 만드는 스크립트 `scripts/build_emb_cache.py` — Chroma 서버에서 **읽기만**(페이지 단위 get), 컬렉션 쓰기 없음. 124만 행. 임시 폴더에 다 쓴 뒤 이름 바꾸기로 교체(쓰는 도중 검색이 반쯤 된 캐시를 읽지 않게).
2. **검색 코드** `_nearest_chunks_per_paper_batched`: `RAG_EMB_CACHE=1` 이면
   - 캐시에 있는 논문 → memmap 에서 임베딩만 읽어 코사인 → 논문별 상위 k 의 **청크 ID 로** `get(ids=…, include=[documents, metadatas])` (~300행).
   - 캐시에 없는 논문(새로 수집된 논문) · `get(ids)` 가 덜 돌려준 논문(재수집으로 ID 바뀜) → 그 논문만 현행 배치 get.
   - 기본 `0`(꺼짐) — 측정 뒤 채택이면 운영 `.env` 에서 켠다.
3. **캐시 갱신**: 매일 수집 뒤 `build_emb_cache.py` 전체 재생성(Chroma 에 "캐시에 없는 것만" 묻는 길이 없어 어차피 전체를 읽는다). 운영 스케줄러에 넣는 것은 **채택 후, 사용자 승인 후**. 그 전에는 캐시 미스가 현행 경로로 떨어지므로 정확성은 유지(속도만 덜 준다).
4. **동치 설계:** 같은 임베딩(Chroma 가 돌려준 float32 를 그대로 저장), 같은 식(float64 로 1 − cos), 논문별 상위 k. 거리가 같은 청크(중복 청크)끼리는 순서가 다를 수 있다 — 동치는 논문별 (거리, 문서) 로 본다.

같은 DB(Chroma 서버, 쓰기 없음), 운영 설정(`RAG_CONTEXT_ABSTRACT=1 RAG_PRESENCE_GATE=1 RAG_COMPARE_SPLIT=1`), 검색만(`eval_e2e_ko.py`):

- 처리 `ec1_*`: `RAG_EMB_CACHE=1`. 비교 25문항(r1 · r2 · g2) + 162.
- 측정 전 동치 확인(통과해야 측정): 실제 DB 에서 논문 5묶음 × 질의 3개, 캐시 경로와 현행 경로의 논문별 상위 k (거리, 문서)가 **전부** 같은지 + 단위 테스트.
