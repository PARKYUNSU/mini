- 청크 ID 는 해시(예 `2f0364…`)라 논문 ID 로 계산할 수 없다 → 행이 어느 논문인지 알려면 메타데이터가 필요하다.

## 1. 가설

배치 get 을 **로컬 임베딩 캐시**(같은 임베딩, 같은 정확 코사인)로 바꾸면 검색 결과는 그대로이고, 비교 질문 지연이 크게 줄며 일반 질문도 줄어든다.

## 2. 바꾸는 것

1. **캐시 파일** `<CHROMA_DB_DIR>_emb_cache/`(운영: `/Volumes/T7 Shield/mini-chroma-rebuild2_emb_cache/`, 약 3.8GB float64 + 인덱스 수십 MB):
   - `emb.npy` (memmap, 행 × 384) · `ids.npy` (청크 ID) · `paper_index.json` (정규화 paper_id → [시작, 끝) 행 범위, 논문별로 연속 배치) · `meta.json` (행 수·만든 시각·컬렉션 행 수).
   - 만드는 스크립트 `scripts/build_emb_cache.py` — Chroma 서버에서 **읽기만**(페이지 단위 get), 컬렉션 쓰기 없음. 124만 행. 임시 폴더에 다 쓴 뒤 이름 바꾸기로 교체(쓰는 도중 검색이 반쯤 된 캐시를 읽지 않게).
2. **검색 코드** `_nearest_chunks_per_paper_batched`: `RAG_EMB_CACHE=1` 이면
   - 캐시에 있는 논문 → memmap 에서 임베딩만 읽어 코사인 → 논문별 상위 k 의 **청크 ID 로** `get(ids=…, include=[documents, metadatas])` (~300행).
   - 캐시에 없는 논문(새로 수집된 논문) · `get(ids)` 가 덜 돌려준 논문(재수집으로 ID 바뀜) → 그 논문만 현행 배치 get.
   - 기본 `0`(꺼짐) — 측정 뒤 채택이면 운영 `.env` 에서 켠다.
3. **캐시 갱신**: 매일 수집 뒤 `build_emb_cache.py` 전체 재생성(Chroma 에 "캐시에 없는 것만" 묻는 길이 없어 어차피 전체를 읽는다). 운영 스케줄러에 넣는 것은 **채택 후, 사용자 승인 후**. 그 전에는 캐시 미스가 현행 경로로 떨어지므로 정확성은 유지(속도만 덜 준다).
4. **동치 설계:** 같은 임베딩(HTTP 클라이언트가 돌려준 **float64** 를 그대로 저장 — §5 18:4x 참고), 같은 식(float64 로 1 − cos), 논문별 상위 k. 거리가 같은 청크(중복 청크)끼리는 순서가 다를 수 있다 — 동치는 논문별 (거리, 문서) 로 본다.

- 수정: 컬렉션 행 수가 캐시를 만들 때(`meta.json` `collection_rows`)와 같으면, 캐시 색인에 없는 논문은 Chroma 에도 없으므로 조회를 건너뛴다(어차피 0행 → **결과 불변**). 행 수는 5분마다 다시 센다 — 수집으로 늘면 예전처럼 현행 경로. 단위 테스트 2개 추가(608 통과).
