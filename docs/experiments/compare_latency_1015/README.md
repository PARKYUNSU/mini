# 비교 질문 지연 줄이기 — 배치 get 나눠 가져오기 + 대상 검색 병렬 (사전 등록, 2026-10-15)

> 측정 **전에** 쓴다. 출발점: [`compare_split_1015/`](../compare_split_1015/) §5 — 비교 질문 지연 중앙값 23.5s → 60.9s (+37s).

## 0. 진단 (2026-10-15, 비교 4문항, 검색만 — `.cron/cs_timing/time_split.py`)

| 질문 | 대상 추출 | 대상 검색 2회 순차 | 병렬 |
|---|---|---|---|
| real2 C01 | 5.9s | 111.9s (**100.5** / 11.4) | 127.5s |
| real2 C02 | 2.9s | 118.4s (4.3 / **114.1**) | 117.8s |
| real2 C03 | 2.9s | 459.2s (4.4 / **454.8**) | 111.5s |
| real2 C04 | 3.6s | 20.3s (5.2 / 15.1) | 15.2s |

- 대상 검색 하나는 보통 4~15s, 가끔 100s 이상. 느린 쪽마다 `BM25 union batched get failed: … too many SQL variables`.
- 원인: `_nearest_chunks_per_paper_batched` 가 주입 논문 전부의 ID 후보(논문당 무버전 + v1..v20 = 21개)를 `$in` 하나로 묻는다. 논문이 많으면 Chroma **서버** SQLite 변수 한도를 넘어 실패하고, 논문마다 필터 벡터 검색(~97회, `_db_lock` 직렬)으로 떨어진다.
- 비교 질문만의 문제가 아니다 — 서버 방식 전환(10-14) 뒤 측정 로그에서 일반 검색도 가끔 실패(cs2 173회 중 10, r2 76회 중 6, lr 237회 중 2, hype 474회 중 4).
- 병렬은 느린 쪽이 지배해서 거의 줄지 않는다 → 먼저 실패를 없앤다.
- 나눠 가져오기 적용 후 같은 4문항(사전 확인): 실패 0, 순차 29~81s · 병렬 26~39s. 배치 get 자체가 논문 112편에 19.6s(HTTP 로 청크 임베딩 전부 전송) — 실패 경로(100~450s)보다는 훨씬 빠르지만 로컬 시절보다 느리다. 임베딩 전송을 줄이는 것은 이 라운드 밖(다음 후보).

## 1. 바꾸는 것

1. **배치 get 나눠 가져오기** (항상 켬, 코드 수정): `$in` 을 `CHROMA_BATCHED_GET_MAX_IDS`(기본 798 = 38편) 개씩 나눠 가져와 합친다. 결과는 한 번에 가져온 것과 같다(`tests/unit/test_batched_get_chunking.py`). 실패하던 경우는 이제 설계한 배치 경로(정확한 코사인)로 간다 — 예전 근사 HNSW 필터 검색과 순위가 약간 다를 수 있다. 대조는 `CHROMA_BATCHED_GET_MAX_IDS=1000000`(한 번에, 옛 동작).
2. **대상 검색 병렬** `RAG_COMPARE_SPLIT_PARALLEL=1` (기본 `0`): 비교 질문의 두 대상 검색을 스레드 2개로. 결과 순서는 대상 순서 그대로.

## 2. 방법

같은 DB(Chroma 서버, 쓰기 없음), 운영 설정(`RAG_CONTEXT_ABSTRACT=1 RAG_PRESENCE_GATE=1 RAG_COMPARE_SPLIT=1`), 검색만:
- 비교 22문항 + 162 `cmp` 2문항(compare_split_1015 와 같은 문항)
  - 대조 `cl0_*`: 옛 동작(한 번에 get), 순차
  - 처리 `cl1_*`: 나눠 가져오기 + 병렬
- 162 전체: 대조 `cl0_162`(한 번에 get) · 처리 `cl1_162`(나눠 가져오기) — 일반 검색 영향 확인. 162 는 비교 질문 2개뿐이라 병렬은 거의 무관.

## 3. 판정

| 지표 | 기준 |
|---|---|
| **주:** 비교 문항 검색 단계 지연 중앙값 | 처리 < 대조 (보고), **처리 ≤ 40s** |
| 비교 22문항 두 편 모두 검색 | 처리가 대조보다 유의하게 낮지 않음(McNemar p ≥ 0.05) 이고 차이 ≤ 1 |
| 162 `ok` | 처리가 유의하게 낮지 않음 |
| 162 검색 지연 중앙값 | 보고 |
| 배치 get 실패 로그 | 처리에서 0 |

채택이면 **사용자 승인 후** 운영 봇 재시작(나눠 가져오기는 코드라 재시작으로 반영) + `.env` `RAG_COMPARE_SPLIT_PARALLEL=1`.

예상: 비교 문항 지연 중앙값 60s 안팎 → 25~35s. 162 `ok` 는 ±2 안.
