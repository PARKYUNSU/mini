# 실험 노트 — 전체 지도 (v4 → v10)

로컬 9B(`Qwen3.5-9B`)를 LoRA SFT 로 운영에 맞게 길들이려는 시도의 기록이다. 일곱 라운드를 돌렸고, **얻은 것은 "무엇이 되는가" 보다 "무엇이 안 되는가" 와 "어떻게 재야 속지 않는가" 쪽이 많다.**

처음 읽는다면 이 순서를 권한다:

1. **[`protocol.md`](protocol.md)** — 측정 규칙. §1 은 우리가 과거에 어떻게 틀렸는지, §3 은 지금까지 확립된 결론이다.
2. 이 문서의 [궤적](#궤적-무엇을-찾아다녔나) — 라운드가 왜 그 순서로 갔는지.
3. **[`prior_work.md`](prior_work.md)** — 문헌 대조. 우리가 본 현상이 알려진 것인지, 안 써본 처방이 무엇인지.
4. 관심 있는 라운드의 `README.md`(계획·가설·판정 **사전** 선언) → `05_conclusion.md`(결과).

## 궤적 — 무엇을 찾아다녔나

**v4~v6: 데이터 축.** "학습 데이터를 고치면 나아진다"는 가정으로 세 라운드를 돌렸다. 계획 슬롯은 실제로 좋아졌지만(16.7% → 4.2%) **코딩은 건드릴수록 나빠졌다.** v6 에서 RAG 이스케이프 결함을 완전히 없앴는데도 코딩이 꿈쩍하지 않은 것이 전환점이었다.

**v7~v8: 도구 축.** 모델이 아니라 **재는 쪽**을 의심했다. v7 에서 추출기를 고치자 실패가 줄었고(v6 코딩 19.4% → 16.7%), v6 에서 "원인에서 뺐던" 이스케이프가 사실은 독립적으로 충분한 결함이었음이 드러났다. v8 은 장황함을 디코딩으로 눌러봤다 — 종료 문제는 거의 사라졌는데 **문제 자체는 안 풀렸다.** 모델이 그 문항의 **코드를 못 쓰는** 것이었고 장황함은 증상이었다.

**baseline_0925/0926: 재는 법.** 문항을 12 → 30 으로 늘리자 불일치 쌍이 4 → 10 개가 되면서 p 가 0.625 → 0.002 로 갈렸다. 그런데 그 유의성이 평가기의 출력 상한에 조건부였다 — 상한을 운영과 맞춰 다시 재니 p=0.004 로 유지됐지만, 실패 **라벨**이 `syntax` 24건에서 `timeout` 35건으로 옮겨갔다. 여기서 규칙이 하나 더 나왔다: **라벨만 보고 원인을 말하지 않는다.**

**v9: 빼기.** 네 라운드가 필터·문항·판정기·디코딩으로 찾아다닌 것을, **그 데이터를 없애는 것**이 해결했다. 코딩 300건을 빼자 코딩 실패가 46.7% → 21.1% 로 떨어져 base 와 통계적으로 구분되지 않게 됐다. 운영 Executor 는 어차피 Groq 이므로 잃을 것도 없었다.

**v10: 하이퍼파라미터 축.** v3~v9 동안 lr 을 2e-4 로 **의도적으로 고정**했는데, 그 결과 문헌이 주 레버로 지목하는 축을 한 번도 안 건드렸다([`prior_work.md`](prior_work.md) §4). 1/4 로 낮춰 돌렸고 — 세 슬롯 불일치 0, 코딩 p=0.500. **아무것도 나빠지지 않았지만 좋아지지도 않았다.**

## 확립된 것

- **코딩 학습 데이터가 코딩 열화의 원인이었다.** 빼면 base 수준으로 돌아온다 (v9, p=1.000). 문헌과도 일치한다 — 자기 증류는 해당 능력을 base **아래로** 끌어내리며 모델이 작을수록 심하다.
- **자기 증류로는 base 를 넘지 못한다.** v4 결론에 적었고 이후 여섯 라운드가 같은 방향이었다.
- **격차는 문제 난도가 아니라 모델 용량이다.** v6 가 실패한 "어려움" 9문항을 Groq `gpt-oss-120b` 는 문항당 2~5초에 **전부** 풀었다 ([`prior_work.md`](prior_work.md) §6).
- **운영에 로컬 코딩은 없다.** Executor 는 Groq 이고, 2026-09-27 에 **로컬 base 폴백**이 배선됐다 — Groq 이 429·장애를 내면 base 가 받는다.

## 방법론이 바뀐 지점 (그리고 그때마다 전부 다시 잰 이유)

측정 도구가 바뀌면 이전 숫자와 비교할 수 없다. 그래서 **바뀔 때마다 비교 대상 전체를 같은 밤에 다시 쟀다.**

| 시점 | 무엇이 바뀌었나 | 다시 잰 것 |
|---|---|---|
| v5 | 잡담 펜스 예외 추가 | 4모델 |
| v7 | 코드 추출기(= 판정기) 교정 | 3모델 |
| baseline_0925 | 문항 12 → 30 | 전부 |
| baseline_0926 | 출력 상한을 운영과 정렬 | 전부 |
| **2026-09-28** | **문항 54 → 70** (제약 문항 16개 추가) | base·v9·v10 예정 |

마지막 확장의 이유는 v10 이 드러낸 **측정의 천장**이다. 세 운영 슬롯에서 base 가 0% 라 파인튜닝이 더 나을 자리가 없었다 — 기존 판정기가 **붕괴 탐지기**(타임아웃·반복·영어 혼입)여서 내용을 채점하지 않기 때문이다. 그래서 기계 검증 가능한 **형식 제약**(정확히 N줄·줄당 N자·JSON만)을 재는 축을 더했다. 지시 따르기는 파인튜닝이 실제로 영향을 주는 능력이고 base 도 자주 틀린다 — 파일럿에서 base 가 16문항 중 7개를 실패했다. 자세한 규칙은 [`protocol.md`](protocol.md) §2.1.

## 쓰라린 교훈 몇 가지

- **대조군 없이는 "수정 효과"와 "그 밤의 운"을 구분할 수 없다.** v7 에서 영향을 받을 수 없는 base 가 움직였고, v10 에서는 base 코딩이 15.6% → 18.9% 로 흔들렸다. 그래서 대조군을 **같은 세션에서** 같이 잰다.
- **단일 측정값을 다음 라운드의 문턱으로 고정하지 않는다.** v6 가 그렇게 했다가 v7 에서 기준선이 노이즈로 움직였다. v10 노트의 초안도 이 금지를 어겼다가 착수 전에 고쳤는데, 그대로 뒀다면 **기준선 이동만으로 통과 판정이 났을 것이다.**
- **한 조작으로 결과가 안 변한 것은 "다른 원인이 있다"는 뜻이지 "이 원인이 아니다"는 뜻이 아니다.** v6 → v7 이 그랬다.
- **판정을 결과보다 먼저 적는다.** 각 라운드 `README.md` §3 이 사전 선언이고, 결과를 본 뒤 바꾸지 않는다.
