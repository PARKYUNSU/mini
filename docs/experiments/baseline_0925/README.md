## ⚠️ 이 결론은 평가기의 토큰 상한에 조건부다 (2026-09-26 추가)

측정 직후에는 이 결과를 "확립된 결론" 으로 적었다. **그 표현은 과했다.**

평가기는 코딩 슬롯에 `num_predict=800` 을 쓰는데, **운영은 4096 이다** (Executor 1차 로컬 = `get_planner_llm` → `OLLAMA_DIRECT_NUM_PREDICT`, 기본 4096, `.env` 미설정). 평가기가 운영보다 **5.1배 엄격**하다.

그런데 v6 의 코딩 실패 36건 중 **16건(44%)이 닫는 펜스가 없는 잘림**이다(`code_unwrap=fence_open`). 실패 응답의 시간 중앙값은 43.8초, 통과 응답은 5.5초다. v6 는 base 보다 장황하므로(코딩 중앙값 12.2s vs 5.4s) 이 상한에 불균형하게 걸린다.

잘림 실패를 전부 통과로 바꾼 **낙관적 상한**을 계산하면:

| | v6만 실패 문항 | McNemar p |
|---|---|---|
| 현재 (상한 800) | 10 | **0.002** (유의) |
| 낙관적 상한 (잘림 전부 통과) | **3** | **0.250** (유의하지 않음) |

즉 **유의성이 평가기 설정에 좌우된다.** 실제 값은 두 극단 사이에 있다 — 토큰을 더 줘도 장황한 응답이 유효한 코드로 끝난다는 보장은 없으므로 잘림 전부가 통과로 바뀌지는 않는다.

**방향은 세 라운드와 일관되지만 유의성은 견고하지 않다.** 평가기 상한을 운영과 맞춰 다시 재기 전까지 이 결과를 확정으로 쓰지 않는다. 슬롯별 상한 대조:

## 격차는 어려움 구간에 있다

| 난이도 | 문항 | base 실패 | v6 실패 |
|---|---|---|---|
| 쉬움 | 6 | 0 | 1 |
| 보통 | 12 | 1 | 2 |
| **어려움** | 12 | **1** | **9** |

v6 만 실패한 10문항 중 8개가 어려움이다. 실패 종류는 대부분 `syntax` 이고 **응답 시간이 49~61초**다 — 코딩 슬롯 토큰 상한(`num_predict=800`)에서 잘린 것이다. base 의 코딩 중앙값은 5.4초, v6 는 12.2초다.

즉 파인튜닝은 **어려운 문제에서 장황해지는 습관**을 만들었고, 그 습관이 상한에 부딪혀 코드가 잘린다. v5~v7 에서 "자기 수정 재작성" 으로 관찰했던 것과 같은 기전이며, 난이도가 올라가자 훨씬 선명해졌다.
