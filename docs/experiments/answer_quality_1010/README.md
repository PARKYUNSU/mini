# 답변 품질 — 정답 논문을 정확히 설명하는가 (기준선, 사전 등록)

- 시작일: 2026-10-10
- 선행: [`../topic_gate_llm_1010/README.md`](../topic_gate_llm_1010/README.md) — 끝단 컨텍스트 적중 0.852. 지금까지의 지표는 "정답 논문이 LLM 컨텍스트에 들어갔는가" 뿐이었다.
- **이 라운드는 기준선이다 — 판정 없음.**

## 1. 측정

1. 답변 생성: `eval_e2e_ko.py --answer --label ans_full` — 162문항, 현행 운영 코드(게이트 2단계·결정적 검색어·1편 규칙 끔), 답변 모델 `yunsur_v9`.
2. 판정: [`scripts/judge_answers.py`](../../../scripts/judge_answers.py) — Groq `openai/gpt-oss-120b`. 정답 논문의 제목·초록과 답변을 주고 JSON 으로:
   - `identifies_paper` — 답변이 그 논문을 결과로 제시하는가
   - `description` — correct / partial / wrong / absent
   - `fabrication` — 초록에 없는 구체 사실(숫자·방법·결과)을 그 논문에 붙였는가
   정답이 여럿(C1)이면 답변이 인용한 정답 중 첫 번째를 기준으로 판정한다.

## 2. 보고할 것

- 162 중 `description = correct` 비율 (주 수치), correct+partial, wrong, fabrication 비율.
- **컨텍스트에 정답이 있었던 문항만** 따로 — 검색 실패와 생성 실패를 가른다.
- 실패 유형 분류(수작업 표본 10개): 인용 ID 혼동 / 수치·내용 날조 / 정답을 무시 / 기타.

## 3. 파일럿 (판정기 확인용, 기준선 아님)

`single_hit_1009` 의 `ans_new` 57문항(1편 규칙 끈 상태)에 판정기를 돌렸다: correct 4 · partial 18 · wrong 15 · absent 20, fabrication 25. 수작업 확인 1건(`A007`): 답변이 CoPE 를 설명하면서 **다른 논문의 ID 를 인용**하고 초록에 없는 "256K → 384,000 토큰" 을 지어냈다 — 판정기 판단이 맞았다. 판정기는 쓸 만하다고 보고 본 측정에 쓴다.

## 4. 예상

- 컨텍스트 적중 문항 중 correct 는 20% 미만, wrong+fabrication 이 다수.
- 주된 실패는 **여러 논문을 받은 답변이 내용과 인용 ID 를 엇갈리게 붙이는 것**(교차 귀속)과 수치 날조.

## 5. 결과 — 부분 기준선 (2026-10-10)

답변 생성은 162문항 모두 끝났다. 판정은 **130문항**(A 114 · C1 13 · C2 3)에서 멈췄다. 이유: Groq 무료 등급의 **하루 토큰 한도 200,000** 을 다 썼고(판정 1회 ≈ 3,500 토큰), **이 한도는 운영 봇의 코딩 Executor 와 같은 키**라 판정을 계속하면 운영 코딩이 막힌다 → 판정을 멈췄다. 남은 29문항(대부분 C1·C2)은 한도가 풀리는 시간에 운영 영향이 적도록 나눠 판정한다.

(판정 중 이어하기가 파일을 처음부터 다시 써서, 멈출 때 행이 잘리는 문제가 있었다 — 백업과 합쳐 복구했고 스크립트는 임시 파일에 쓰고 끝에서 교체하도록 고쳤다.)

| 판정된 130 중 | correct | partial | wrong | absent | 날조 |
|---|---|---|---|---|---|
| 전체 | **5** | 49 | 28 | 48 | 54 |
| 컨텍스트에 정답 있음 (113) | **5 (4.4%)** | 49 | 28 | 31 | 53 (47%) |
| 그중 답변이 정답 ID 를 인용 (79) | 5 | 44 | **26** | 4 | 45 |

**읽은 것**
- 검색이 정답을 컨텍스트에 넣어 줘도 답변이 그 논문을 **정확히** 설명하는 경우는 4.4% 다. 정답 ID 를 인용한 79개 중 26개는 **ID 는 맞는데 내용이 틀렸다** — 다른 논문의 내용을 그 ID 에 붙이는 교차 귀속.
- 날조(초록에 없는 숫자·방법)는 컨텍스트 적중 답변의 47%.
- 예상(correct 20% 미만, wrong+날조 다수, 주된 실패는 교차 귀속): 맞음 — 예상보다 더 나쁘다.

**다음 후보 (선언 전)**: 답변 모델 비교(base `qwen3.5:9b` · `yunsur_v9` · Groq — 같은 컨텍스트로), 컨텍스트 형식(논문마다 ID 와 제목을 문단 머리에 두고 "인용은 그 문단의 ID 만"), 답변 템플릿의 '본론 N개 항목' 구조가 여러 논문을 섞게 만드는지.

## 6. 다음 라운드 사전 등록 (2026-10-10) — 판정자 교체 확인 → base vs v9

Groq 판정은 운영 코딩과 하루 한도를 같이 쓰므로, 판정을 **Claude(Opus 5.5, 이 작업 세션)** 가 직접 하는 안을 확인한 뒤 답변 모델을 비교한다. 아래는 측정 전에 고정한다.

### 6.1 1단계 — 판정자 일치도 (Claude vs gpt-oss-120b)

- 대상: §5 에서 gpt-oss 가 판정한 **130문항**. 입력·기준은 `judge_answers.py` 의 PROMPT 와 같다(질문, 정답 논문 ID·제목·초록[:2000], 답변).
- 눈가림: Claude 는 gpt-oss 판정을 보기 전에 판정한다. 판정용 파일에는 질문·정답 논문·답변만 넣고(`claude_judge_input.jsonl`), 판정은 `judged_claude_ans_full.jsonl` 에 저장한 다음에 비교 스크립트로 맞춘다.
- 지표:
  - **주 지표 `ok` = description ∈ {correct, partial}** (논문을 적어도 부분적으로 맞게 설명) — 이진 일치율과 Cohen κ.
  - description 4분류 일치율·혼동표, fabrication 일치율·κ.
- 채택 기준: **`ok` 일치율 ≥ 0.85 그리고 κ ≥ 0.60**, fabrication 일치율 ≥ 0.75. 못 미치면 Claude 를 판정자로 쓰지 않고 Groq 판정을 하루 50문항씩 나눠 한다.
- 어느 쪽이 더 엄격한지(혼동표의 비대각 방향)도 보고한다 — 2단계에서 절대값이 아니라 **짝 비교**만 쓰는 이유.

### 6.2 2단계 — 답변 모델 비교 (base `qwen3.5:9b` vs `yunsur_v9`)

- 생성: `RAG_ANSWER_MODEL=qwen3.5:9b` 를 **평가 프로세스에만** 주고 `eval_e2e_ko.py --answer --label ans_base` (운영 `.env`·`LOCAL_LLM_MODEL` 은 건드리지 않는다).
- 같은 컨텍스트: 검색어 추출은 결정적(temperature 0, seed 0)이라 컨텍스트가 같아야 한다. `context_papers` 가 `ans_full` 과 **다른 문항은 비교에서 뺀다**(수를 보고).
- 판정: 1단계를 통과한 판정자로 두 모델 답변을 모두 판정한다. Claude 가 판정하면 두 답변을 **섞고 모델 이름을 가린 채** 판정한다.
- 대상: 두 쪽 모두 RAG 경로(`direct_answer/B`)이고 **컨텍스트에 정답이 있었던** 문항.
- 주 지표: `ok` 짝 비교, McNemar 정확 검정(양측, α=0.05). 부 지표: correct, fabrication, "ID 맞고 내용 틀림".
- 판정 규칙:
  - base 가 유의하게 낫다 → v9 파인튜닝이 내용 정확도를 해친다. RAG 답변 모델을 base 로 되돌리는 안을 따로 제안한다(형식 실패율도 같이 확인).
  - 유의차 없음 → 모델이 아니라 컨텍스트 형식·답변 템플릿을 고친다(§5 다음 후보).
  - v9 가 유의하게 낫다 → v9 유지, 같은 결론.
- 예상: 둘 다 낮다(correct < 15%). v9 와 base 의 `ok` 차이는 유의하지 않을 것 — 교차 귀속은 모델보다 컨텍스트 형식 탓이라고 본다.
