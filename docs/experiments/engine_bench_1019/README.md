# 추론 엔진 속도 비교 — Ollama(llama.cpp) · MLX · uzu (사전 등록, 2026-10-19)

> 측정 **전에** 쓴다. 1단계(엔진 속도만). 운영은 바꾸지 않는다. 출발점: [`status_1018/`](../status_1018/) — 응답 중앙 52s 중 답변 생성 ~20s(16 토큰/s) · 문서 읽기 ~15s(163 토큰/s).
> 계기: 사용자가 찾은 비교(llama.cpp · MLX · uzu by Mirai, Qwen3.5 9B 4bit).

맥미니 Apple **M2** 16GB, macOS 26.6.2.

양자화 방식이 엔진마다 달라 **품질은 이 단계에서 비교하지 않는다**(속도만). 우리 답변 모델 `yunsur_v13` 은 2단계에서 다룬다.

## 1. 방법

- 입력: 운영 답변 프롬프트 그대로 20개 — `s18_162` 저장 컨텍스트로 `direct_answer_rag_user` 를 다시 만든 것(system + user, 2,000~3,300 토큰 급). lat_profile 과 같은 20문항.
- 호출: 엔진마다 같은 측정 코드(OpenAI 호환 스트리밍), `temperature 0`, `max_tokens 400`, 사고 모드 끔(가능한 방법으로). 엔진마다 예열 1회 후 20개.
- 잰다: **첫 토큰까지 시간(TTFT ≈ 문서 읽기)**, **생성 속도(토큰/s, 첫 토큰 뒤)**, 전체 시간, 생성 토큰 수.
- **앞부분 재사용**: 10문항에 대해 판정형 메시지(같은 앞부분 + 다른 꼬리)를 먼저 보내고 바로 답변 프롬프트를 보내 TTFT 를 잰다(지금 운영의 판정 캐시가 기대는 성질).
- 메모리: 엔진 서버 프로세스 RSS 최대.
- 한 번에 한 엔진만 띄운다(16GB). 측정 중 Ollama 모델은 내리고, 운영 봇은 켜 둔다(질문이 오면 섞일 수 있음 — 시간대 기록).

## 2. 판정 (측정 전 고정)

- **"답 하나 시간" 추정** = 문서 읽기(TTFT) + 400 토큰 생성 시간, 20문항 중앙. 엔진 X 가 Ollama 보다 **20% 이상 짧고** 20문항 중 **16개 이상**에서 짧으면 2단계(v13 변환 · 품질 확인) 후보.
- 앞부분 재사용이 안 되는 엔진은, 판정 문항에서 읽기를 두 번 하는 비용(~TTFT 1회)을 더해서 다시 비교한다.
- 설치·실행이 안 되거나 Qwen3.5 9B 를 못 올리면 "후보 아님"으로 적는다.

## 4. 결과 (2026-10-19) — **두 후보 모두 기준 미달 → 2단계 안 감. 운영은 Ollama 그대로**

같은 20 프롬프트(중앙 2,784 토큰), 생성 400 토큰 상한, greedy, 사고 끔.

| 엔진 | 읽기 (TTFT 중앙) | 읽기 속도 | 생성 속도 | **답 하나 추정** (읽기 + 400 토큰) | Ollama 대비 | 빠른 문항 | 메모리 |
|---|---|---|---|---|---|---|---|
| **Ollama** (llama.cpp, 지금) | 17.0s | **164 tok/s** | 16.3 tok/s | **41.7s** | — | — | ~6.3GB |
| MLX (mlx-lm) | 20.3s | 137 tok/s | **18.4 tok/s** | 42.4s | 1.01배 | 2/20 | 6.6GB (peak) |
| uzu (Mirai) | 22.1s | 128 tok/s | **18.6 tok/s** | 43.6s | 1.04배 | 0/20 | 5.8GB |

판정 기준(20% 이상 짧고 16/20 이상): 둘 다 미달.

**앞부분 재사용** (판정 → 답변, 10문항):
| | 판정 TTFT | 답변 TTFT (cold 대비) | 비고 |
|---|---|---|---|
| Ollama | 1.9s | 3.3s (17.4s) | 자동. llama-server 가 RAM 프롬프트 캐시를 들고 있어 판정조차 본측정 때 읽은 앞부분을 재사용했다 |
| MLX | 1.5s | 3.6s (20.6s) | **직접 캐시를 복사해야** 된다(공통 앞부분을 한 번 읽고 `deepcopy`) — 봇 코드에 구현 필요 |
| uzu | 19.5s | 22.7s (22.7s) | **재사용 안 됨**(`tokens_count_input_cached` 0, 세션마다 새로 읽음) — 판정 캐시 효과(~14s)를 잃는다 |

**읽은 것**
- 두 엔진 모두 **생성은 13~14% 빠르지만 읽기가 16~22% 느려** 서로 상쇄된다. 우리 봇은 문서를 ~2,800 토큰 읽고 ~350 토큰 쓰는 '읽기 무거운' 작업이라 읽기 속도가 더 중요하다.
- uzu 는 재사용이 안 돼, 판정 캐시를 쓰는 지금 운영과 비교하면 문항당 ~15s 더 느려진다.
- 사용자가 본 비교 그림은 짧은 프롬프트 생성 속도 위주로 보인다(우리 조건과 다름). 맥미니 M2(기본형)라는 점도 다르다 — 더 큰 칩에서는 결과가 다를 수 있다.
- 생성 속도 이득(~2 tok/s)만으로는 답 하나에 ~3s 정도 — 엔진 교체 · v13 변환 · 재사용 구현 비용에 비해 작다.

정리: 이 하드웨어 · 이 작업에서는 **Ollama(llama.cpp) 가 이미 가장 빠르다**. 받은 모델(MLX 5.6GB T7 `hf_bench/` · uzu 5.6GB `~/.cache/mirai`)과 venv(`~/venvs/enginebench`, 536MB)는 **10-19 사용자 요청으로 삭제**(삭제 뒤 경로 없음 확인). 측정 스크립트 · 결과(`.cron/bench/`)는 남김. Ollama 모델은 그대로.
