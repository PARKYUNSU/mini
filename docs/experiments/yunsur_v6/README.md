## 1. 문제 정의

v5의 코딩 실패 4건은 원인이 v4 진단과 달랐다.

v4에서는 "코드 안 긴 한국어 주석 → 토큰 상한(800)에서 잘림"으로 보고, v5에서 **주석 비율 >30% 거절** 필터를 넣었다. 필터는 데이터에서 작동했다 — 코딩 주석 비율 p95 0.42 → 0.16, 학습 토큰 잘림 0건. 그런데 실패율은 16.7% → 22.2%로 오히려 올랐다.

실패 원문을 보면 행동이 다르다.

```
fibonacci.append(sum(fibonacci[-2:]) if len(fibonacci) >= 2 else None # 단순화 로직 수정 필요 없음 (다음 코드 참조)

# 올바른 구현으로 재작성 및 출력합니다.

def generate_fibo(n):
    fib = [0, 1] * n + []
```

구현을 한 번 쓴 뒤 **주석으로 자기 코드를 의심하고 두 번째 구현을 시작**한다. 그러다 상한에 걸려 표현식 중간에서 잘리고 `syntax` 또는 펜스 미닫힘이 된다. 주석은 이 행동의 흔적이지 원인이 아니다. 같은 패턴이 `yunsur_v4_merged` 에도 있으므로 **베이스에서 온 습관**이다.

### 평가 세트가 이 문제를 가리고 있었다

현재 코딩 6문항 중 5개가 한 줄짜리다.

| id | 요청 | 성격 |
|---|---|---|
| coding_01 | 1부터 10까지 합 | 한 줄 |
| coding_02 | 리스트 정렬 | 한 줄 |
| coding_03 | 문자열 길이 | 한 줄 |
| coding_04 | 1~20 짝수 출력 | 한 줄 (반복문) |
| coding_05 | 딕셔너리 값 합 | 한 줄 |
| coding_06 | 피보나치 앞 10개 | **루프 + 상태** |

v5의 코딩 실패 4건은 `coding_06`(3/3 전부)과 `coding_04`(1회)에서 나왔다. 즉 "코딩 22%"는 사실상 **유일하게 사소하지 않은 문항이 매번 실패한다**는 뜻이고, 지금 표본으로는 "슬롯 전반의 악화"와 "한 유형의 재현성 있는 실패"를 구분할 수 없다.

## 2. 가설

- **H1: 코딩 실패는 자기 수정 재작성 행동이다.** → 학습 데이터에서 **코드 블록 2개 이상**이거나 **자기 수정 표현**이 있는 샘플을 거절하면, 모델이 "한 번에 하나의 구현"을 쓰고 `syntax`·펜스 미닫힘이 줄어든다.
- **H2: 실패는 난이도에 붙어 있다.** → 난이도를 분포시킨 12문항에서, 실패는 쉬움 구간이 아니라 보통·어려움 구간에 몰린다. (H1이 맞다면 v6는 그 구간에서 v5보다 낮아진다.)
- **H3: 잡담·계획은 v5 수준을 유지한다.** (데이터를 건드리지 않았으므로)
- **H4: 코딩 실패의 일부는 RAG 데이터에서 새어 나온 이스케이프 습관이다.** → RAG 400건의 literal `\n` 을 진짜 개행으로 고치면, 응답의 literal `\n` 유출이 사라지고 `coding_10` 류 3건이 없어진다. RAG 슬롯 자체의 실패율(0%)은 나빠지지 않는다.

하이퍼파라미터는 v3 = v4 = v5 = **v6로 계속 고정** (LoRA r16/α32, lr 2e-4, 1 epoch, seq 2048, adamw_8bit, seed 3407). 슬롯별 건수도 400/300/400/300 그대로 — 건수 효과와 섞이지 않게 한다. **바뀌는 것은 코딩 거절 필터와 RAG 이스케이프 수정, 두 가지다.**

H1과 H4는 서로 다른 실패를 겨냥하므로 결과에서 분리해 읽을 수 있다: H4가 맞으면 응답의 literal `\n` 빈도가 0에 가까워지고 `coding_10` 이 통과한다. H1이 맞으면 `coding_06` 류의 `syntax`·펜스 미닫힘이 준다. 둘 중 하나만 맞는 경우도 구분된다.

## 3. 성공 기준 (사전 선언 — 결과를 본 뒤 바꾸지 않는다)

평가 세트가 30 → 36문항으로 바뀌므로 **v5 라운드의 숫자와 직접 비교할 수 없다.** 따라서 기준을 절대 수치가 아니라 **같은 세트에서 재측정한 base·v5에 대한 상대 규칙**으로 선언한다. base와 v5는 **v6 학습 전에** 새 세트로 재측정하고 그 숫자를 고정한다 (§5).

같은 36문항 × 3회 (n=108), 같은 프롬프트, 3모델을 같은 밤에 측정한 결과에서:

- **통과**: v6 코딩 strict가 **base 코딩 strict + 5%p 이내**이고, 잡담·RAG·계획이 **v5 대비 +5%p 이내**.
- **부분 통과**: v6 코딩 strict가 **v5 코딩 strict의 절반 이하**이고, 다른 슬롯이 v5 대비 +5%p 이내 → "H1 유효, base 도달은 미달"로 기록.
- **실패**: v6 코딩이 v5보다 **+5%p 이상 악화**, 또는 다른 슬롯이 v5 대비 **+5%p 이상 악화**.

판정 예외는 v5와 동일하다 (잡담 펜스 예외 `TEMPLATE_REQUEST_RE`). 3모델에 같은 판정기를 쓴다.

### 기준값 (2026-09-23 08:02→09:11, 68분, 36문항 n=108, 판정기 커밋 `fe20b5a`, 세트 sha256 `a1cfe0f7f562`)

| 슬롯 | base strict (hard) · 중앙값 | v5 strict (hard) · 중앙값 |
|---|---|---|
| 잡담 | 0% (0) · 4.6s | 0% (0) · 4.9s |
| 계획 | 0% (0) · 5.5s | 0% (0) · 5.5s |
| RAG | 12.5% (0) · 30.9s | **0%** (0) · 32.2s |
| 코딩 | **11.1%** (8.3%) · 4.4s | 25% (22.2%) · 5.7s |
| 전체 | 6% (3%) | 8% (7%) |

코딩 난이도별 (기록용): base 쉬움 0/18 · 보통 3/12 · 어려움 1/6 → v5 쉬움 4/18 · 보통 3/12 · 어려움 2/6.

**위 표에서 파생되는 v6 판정선** (이제 절대 수치로 고정한다):

- **통과**: v6 코딩 strict **≤ 16.1%** (base 11.1% + 5%p) **and** 잡담 ≤5% · 계획 ≤5% · RAG ≤5% (각각 v5 + 5%p)
- **부분 통과**: v6 코딩 strict **≤ 12.5%** (v5 25% 의 절반) **and** 다른 슬롯이 위 상한 이내
- **실패**: v6 코딩 **≥ 30%** (v5 + 5%p), 또는 다른 슬롯이 v5 대비 +5%p 이상 악화

조항은 통과 → 부분 통과 → 실패 순으로 본다. base 코딩이 0%가 아니라 11.1%로 나오는 바람에 **통과선(16.1%)이 부분 통과선(12.5%)보다 느슨해졌다.** 규칙 자체는 v6 결과를 보기 전에 선언한 것이므로 그대로 두고, 이 역전은 해석에서 감안한다.

**판정 기준에 넣지 않고 기록만 하는 것**: 난이도 구간별(쉬움/보통/어려움) 실패율, 중앙값 응답시간, 실패 응답의 코드 블록 개수. H2는 이 기록으로 판단하되 통과/실패 판정에는 쓰지 않는다 — 난이도 구간은 문항 수가 적어 판정에 쓸 만큼 안정적이지 않다.

| 합계 | 1,400 | **1,400** | | |

### RAG 이스케이프 수정

v5 학습 데이터의 RAG 400건 중 **175건(44%)** 이 개행을 literal `\n`(역슬래시+n 두 글자)으로 담고 있다. 출처는 전부 `v3_clean` 이고, v4 에도 164건 있었다 — v3 파이프라인에서 이스케이프가 한 번 더 먹은 것이 그대로 상속됐다.

```
'## 서론\\n대규모 언어 모델(LLM)이 128K에서 1M 토큰에...'
```

기준선 측정의 대조가 원인을 확정한다. **base 는 108건 전부 literal `\n` 을 쓰지 않는데, v5 는 RAG 24/24 전부, 잡담 3/24, 코딩 3/36 에서 쓴다.** 학습으로 생긴 습관이고, 코딩에서는 코드 추출이 깨져 `syntax` 실패가 된다.

RAG 슬롯이 0% 라서 이 결함이 가려져 있었다 — 판정기가 literal `\n` 을 보지 않으므로 RAG 에서는 무해해 보이고, 피해는 다른 슬롯에서 난다.

수정은 RAG 샘플의 `output` 에서 이스케이프된 개행만 되돌린다. **코딩 샘플의 literal `\n` 2건은 건드리지 않는다** — `sep='\n'`, `text.replace("\n","")` 처럼 파이썬 코드 안의 진짜 문자열이라 정상이다.

**판정기는 바꾸지 않는다.** literal `\n` 을 품질 실패로 추가하면 §3 의 기준선을 다시 재야 한다. 대신 **응답의 literal `\n` 빈도를 기록 지표로 둔다** (결과 jsonl 에서 사후 집계, 판정 아님).

### 코딩 거절 필터 교체

- **뺀다**: 주석 비율 >30% 거절 (`comment_heavy`) — v5에서 데이터 지표만 개선하고 실패율은 못 줄인 것이 확인됐다. 남겨두면 필터 두 개의 효과가 섞인다.
- **넣는다**:
  - `multi_block`: 응답에 코드 블록이 2개 이상
  - `self_revision`: 코드 또는 산문에 자기 수정 표현 — "재작성", "수정 필요", "또는 다음과 같이", "더 간결한", "올바른 구현", "다시 쓰면" 류
- 유지: 코드 300줄 이하, 평가 문항과 유사도 ≥0.72 제외

거절률과 거절 사유 분포는 `02_data_design.md` 에 기록한다. v5 코딩 raw 에 이 필터를 **소급 적용**해 몇 건이 걸리는지 먼저 확인한다 (v5 때 `--import-v4-raw` 로 했던 방식).

## 5. 평가 세트 변경 (36문항)

코딩 6 → **12문항**. 나머지 슬롯(잡담 8 / RAG 8 / 계획 8)은 건드리지 않는다.

| 구간 | 문항 | 성격 |
|---|---|---|
| 쉬움 | `coding_01`~`coding_06` | 기존 유지. 5개는 한 줄, `coding_06`만 루프+상태 |
| 보통 | `coding_07` 누적합 · `coding_08` FizzBuzz · `coding_09` 글자 수 집계 · `coding_10` 문자열→딕셔너리 파싱 | 루프+상태, 조건 분기, 딕셔너리 집계, 문자열 파싱 |
| 어려움 | `coding_11` `second_largest`(중복·길이 부족 시 None) · `coding_12` 중첩 자료구조 평균 | 함수 정의 + 경계 조건, 중첩 자료구조 처리 |

문항은 전부 **자기완결**이다 — 파일·네트워크·`input()` 없이 그대로 실행돼야 한다 (`_coding_ok` 가 임시 디렉터리에서 8초 제한으로 실제 실행한다).

- 새 6문항은 학습 데이터(v5 코딩 raw + v6 재생성분)와 **유사도 ≥0.72 이면 제외**한다 — v4·v5와 같은 격리 규칙.
- 판정기(`_coding_ok`: `ast.parse` + 금지 호출)는 **바꾸지 않는다.** 난이도를 올리되 채점 방식은 고정한다.
- 세트를 바꾼 직후 **base·v5를 새 36문항으로 재측정**하고 그 숫자를 `04_eval_v6/` 에 고정한다. v6 학습·측정은 그 다음이다. (약 2시간, 맥미니)
