# 이름 붙은 논문 찾기 (사전 등록, 2026-11-01)

> 측정 **전에** 쓴다. 출발점: 10-30 실사용 R_138("… atomic claim 단위로 S/U 판정한다. **FActScore** 계열이다. …")에서 FActScore 를 못 찾았다. corpus_llmeval_1030 에서 DB 에 넣은 뒤에도 못 찾았고(answer_review_1030 · 10-31 재질문), 원인은 검색 쪽이다.

## 1. 원인 (dev 진단)

- 검색은 9B 가 만든 영어 검색어로 한다. R_138 의 검색어는 `factscore, faithfulness filter, atomic claim judgment protocol` — 이름이 소문자가 된다. BM25 단독으로는 FActScore(2305.14251)가 4위인데, 하이브리드(벡터 0.55 + BM25 0.45 + 가벼운 재순위) 순위는 21위(상위 40 안, 15 밖)라 컨텍스트에 못 든다.
- 이름을 지키는 기존 장치는 셋인데 다 못 잡는다:
  - 제목 먼저 넣기(`_find_paper_by_title`)는 검색어 전체와 제목의 토큰 겹침이 0.6 이상이어야 한다.
  - 제목 가산(`HYBRID_TITLE_BOOST`)은 검색어 전체가 제목에 들어 있어야 한다.
  - 관련 문서 거르기의 이름 보호(`relevance_filter.protected`)는 15편 안에 있을 때만 쓰인다.
- dev 세트(162 · real40 · real2 · llm · er · sub · g · survey)에서 정답이 질문 속 이름과 제목이 맞는 논문인 질문 26개는 지금도 **26/26 상위 5** 다. 이름이 질문의 주제일 때는 이미 찾는다. 놓치는 것은 이름이 곁가지로 나오는 긴 질문(R_138)이다.

## 2. 변경 — `RAG_NAME_LOOKUP=1` (기본 끔)

- **질문 원문**(사용자 글 — 9B 검색어 아님)의 고유 이름을 관련 문서 거르기와 같은 규칙(`relevance_filter.names`, 대소문자 그대로)으로 뽑는다.
- 이름마다 BM25 색인 제목에서 찾는다(`BM25Searcher.named_paper`, 대소문자 그대로 · 단어 경계). `이름:` 으로 시작하는 제목이 하나면 그 논문, 아니면 이름이 든 제목이 하나뿐일 때만 고른다. 질문당 최대 3편.
- 고른 논문이 후보에 없으면 BM25 합집합 주입과 같은 방식(같은 검색어로 그 논문의 가장 가까운 청크와 실제 거리)으로 넣는다. 상위 15 자르기에서 보호하고(`protect_pids`), 결과 **맨 앞**(이름이 나온 순서)에 둔다. 관련 문서 거르기가 이름 든 제목을 지키므로 상위 5 에 남는다.
- 경로: 직답 검색 · 목록 모드 검색 · 비교 분리 검색(대상 글). 라우터 검색은 안 바꾼다 — 운영은 `RAG_ROUTER_RESEARCH=1` 이라 직답에서 다시 검색한다.
- 이름이 없거나 맞는 제목이 없는 질문은 코드가 그대로 돈다(`tests/unit/test_name_lookup.py`, 단위 테스트 702 통과).

## 4. 측정

- 검색만 잰다(`--answer` 없음 · `--save-context`). 33문항을 이름 찾기 끔(`nl0_*`) · 켬(`nl1_*`)으로 한 번씩(`run.sh`). 검색어 LLM 은 temperature 0 · seed 고정(`agent_llm`)이고, 거르기도 temperature 0 이다.
- 채점 `score.py`: 문항마다 상위 5(`context_papers`) 끔 → 켬, 이름 논문 위치, 밀려난 논문, 검색 단계 시간.

## 5. 판정 (측정 전 고정)

버그 고침으로 본다. 바뀌는 문항이 적어 protocol §2.5 의 부호 검정 문항 수를 못 채우므로 효과 크기는 주장하지 않는다. 아래를 **모두** 만족하면 채택(운영 `.env` 켜기 제안 — 사용자 승인 필요), 하나라도 어기면 기각.

1. R_138: 켬에서 FActScore(2305.14251)가 상위 5 안.
2. held-out: 정답 있는 4문항(B01 · B02 · B05 · B10)이 켬에서 정답을 상위 5 에 가진다. 끔보다 정답을 잃은 held-out 문항 0.
3. dev: 끔보다 켬에서 정답을 잃은 문항 0 (정답 있는 문항).
4. 검색 단계 시간 중앙 증가 ≤ 1s.

보고: 끔에서 이름 논문이 이미 상위 5 였던 문항 수 · 올라온 이름 논문 · 밀려난 논문 · 정답 없는 문항(R_139 · D02 · D06 · F08 · LLM-as-a-judge)의 변화. 답 품질(이름 논문이 맨 앞에 와서 답이 곁가지로 쏠리는지)은 재지 않는다 — 검색 변경은 검색만 잰다(§2.5).
