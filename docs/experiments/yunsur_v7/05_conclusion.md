## 1. 결함이 셋 겹쳐 있었다 — 그리고 앞선 진단을 정정한다

v6 결론에 "`ast.parse` 를 깨뜨린 것은 이스케이프가 아니라 **붙은 펜스**였다"고 적었다. **이 표현은 너무 강했다.**

이번 라운드의 v5 응답을 보면 분명하다.

```
v5: "```pythonimport ast\\ns = 'name=kim;age=30;city=seoul'\\ndict_result = {...}"
v6: "```pythonimport re\n\ndata_str = 'name=kim;age=30;city=seoul'\n..."
```

(v5 의 `\\n` 은 literal 두 글자, v6 의 `\n` 은 진짜 개행)

펜스를 복구해도 **v5 는 여전히 한 줄짜리 literal `\n` 문자열**이라 `ast.parse` 가 깨진다. v5 는 이스케이프를 고치지 않았으므로 당연하다.

정확한 서술은 이렇다. `coding_10` 에는 **독립적으로 각각 충분한** 결함이 둘 있었고(이스케이프·붙은 펜스), 그 아래에 **모델이 쓴 코드 자체의 문제**가 하나 더 있었다.

| 모델 | 이스케이프 | 붙은 펜스 | 결과 |
|---|---|---|---|
| v5 | ✗ 있음 | ✗ 복구됨 | 3/3 실패 (literal `\n` 때문) |
| v6 | ✅ 고침 | ✅ 복구됨 | **1/3 통과**, t2 `syntax`(모델이 쓴 코드가 깨짐), t3 `runtime` |
| base | ✅ 없음 | ✅ 없음 | 1/3 실패 (`runtime`) |

v6 의 남은 2건은 도구 문제가 아니다. t3 은 `int(value.replace('"', ''))` 로 `'kim'` 을 정수 변환해 `ValueError` 를 내는데, **base 가 같은 문항에서 내는 것과 같은 오류**다(기준선에서 확인). t2 는 정의되지 않은 이름을 참조하는 망가진 컴프리헨션이다.

즉 **도구 결함을 둘 다 걷어내자 남은 것은 "모델이 이 문항에서 코드를 잘못 쓴다" 뿐이고, base 도 같은 자리에서 틀린다.**

## 2. 측정 해상도가 결론을 좌우한다 — 이번 라운드의 가장 큰 발견

P1 이 빗나간 것이 핵심 신호다. base 는 붙은 펜스가 0/36 이므로 추출기 수정의 영향을 받을 수 없는데도 코딩이 11.1% → 8.3% 로 움직였다. 순수 노이즈다.

세 라운드에 걸친 같은 모델의 변동폭:

| 측정 | base 코딩 | base RAG | base 계획 | v5 코딩 | v5 계획 |
|---|---|---|---|---|---|
| 09-23 (v6 기준선) | 11.1% | 12.5% | 0% | 25% | 0% |
| 09-24 (v6 라운드) | — | — | — | 19.4% | 0% |
| 09-25 (v7, 추출기 수정) | **8.3%** | **4.2%** | **4.2%** | 16.7% | **4.2%** |

n=24 에서 1건은 4.17%p, n=36(코딩) 에서 1건은 2.78%p 다. 위 변동은 전부 **±1~2건**이다. 그런데 §3 판정선은 **±5%p** — 즉 **판정선이 측정 노이즈와 같은 크기다.**

v6 라운드에서 이 위험을 기록만 하고 넘어갔는데("경계에 가까운 결과였다면 판정을 신뢰할 수 없었다"), 이번에 실제로 그 일이 일어났다. **이 해상도로는 데이터 라운드를 더 돌려도 결론을 못 낸다.**

## 3. 판정선 갱신 — 쓰지 않는다

v7 의 새 기준선을 고정하려 했으나, §2 의 결과를 보면 **단일 측정값을 기준선으로 박는 것 자체가 잘못**이다. 같은 모델이 밤마다 ±1~2건 움직이는데 한 밤의 숫자를 고정값으로 쓰면 다음 라운드 판정이 그 밤의 운에 좌우된다.

따라서 v8 은 판정선을 세우기 전에 **측정 해상도부터 올린다**(§4).

참고로 이번 라운드까지의 코딩 strict 를 모아 두면: base 8.3~11.1%, v5 16.7~25%, v6 19.4~22.2%. **파인튜닝 모델이 base 보다 코딩에서 나쁜 것은 세 라운드 모두 일관**되며, 이 결론은 노이즈보다 크다.

## 4. 다음 라운드(v8)에 반영할 것

1. **반복을 3 → 10 회로 올린다.** n=108 → 360. 코딩 1건의 가중치가 2.78%p → 0.83%p 가 되어 ±5%p 판정선이 의미를 갖는다. 측정 시간은 모델당 약 30분 → 100분이므로, **측정 대상을 base 와 신모델 둘로 줄여** 약 3.5시간에 맞춘다.
2. **기준선을 단일 측정에서 2회 평균으로 바꾼다.** 또는 반복을 올린 뒤 한 번만 재되, 그 값의 신뢰구간을 같이 기록한다.
3. **남은 코딩 실패는 모델이 쓰는 코드의 질 문제다.** `coding_10`·`coding_06`·`coding_11` 에서 과잉 설계(요청하지 않은 타입 변환·정규식)와 자기 수정 재작성이 반복된다. base 도 같은 자리에서 틀리므로(base 코딩 8.3%), **"base 를 넘는다"가 아니라 "base 만큼 한다"를 목표로 재설정할 것**을 권한다.
4. 추출기 수정은 유지한다. 실패율 기여는 작았지만(v6 `coding_10` 1시행) 운영 Executor 노드가 같은 코드를 쓰고, `+fused` 표시로 결함을 계속 셀 수 있다.

## 실험 과정에서 얻은 교훈 (실패 기록)

- **"A 가 아니라 B 였다" 는 서술을 조심한다.** v6 에서 B(붙은 펜스)만으로 실패가 나는 것을 보고 A(이스케이프)를 원인에서 뺐는데, 둘은 **각각 독립적으로 충분한 원인**이었다. 한 조작으로 결과가 안 변한 것은 "다른 원인이 있다"는 뜻이지 "이 원인이 아니다"는 뜻이 아니다.
- **영향을 받을 수 없는 대조군을 항상 같이 잰다.** base 는 붙은 펜스가 0/36 이라 추출기 수정의 영향을 받을 수 없다. 그 base 가 움직였다는 사실이 이번 라운드에서 가장 유용한 정보였다 — 노이즈 크기를 직접 보여줬다.
- **도구를 고칠 때는 고친 사실을 세어 둔다.** `+fused` 표시 덕분에 "복구가 실제로 3건씩 일어났다"(P4)를 확인할 수 있었고, 실패율이 안 움직인 것을 "수정이 안 먹었다"와 구분할 수 있었다.
