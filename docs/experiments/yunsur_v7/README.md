## 1. 문제 정의

v6 재측정에서 `coding_10` 이 v5·v6 모두 3/3 실패했다. 원문은 이렇다.

```
```pythonimport re

data_str = 'name=kim;age=30;city=seoul'
```

여는 펜스의 언어 태그와 첫 코드 줄 사이에 개행이 없다. 추출기의 펜스 정규식이 언어 태그를 `pythonimport` 로 읽어 매치에 실패하고, 전체가 `plain` 으로 떨어져 `ast.parse` 가 깨진다.

이 결함의 성격은 v6 결론에서 확정됐다.

| | 붙은 펜스 |
|---|---|
| 학습 데이터 (v5·v6 코딩 300건) | **0건** |
| base | **0/36** |
| v5 (두 밤) · v6 | 각 **3/36** — 전부 `coding_10`, 전부 실패 |

학습 데이터를 베낀 것이 아니라 **생성 시점에 생긴다.** 그래서 데이터 필터로는 못 잡는다. 발동 조건은 좁다 — **코드가 `import` 로 시작할 때만**이고(base 는 그런 응답이 0/36, v6 는 3/36 이며 그 3/3 이 모두 붙었다), 학습 데이터 코딩의 23.3%가 `import` 로 시작한다(형식은 전부 정상).

### 왜 추출기를 고치는가 — 그리고 무엇을 가리지 않는가

` ```pythonimport re ` 는 마크다운으로도 잘못된 출력이다(렌더러는 언어명을 `pythonimport` 로 읽는다). 추출기를 관대하게 만드는 것은 **모델 결함을 가리는 쪽**이기도 하다.

그래도 고치는 이유는 운영이다. 같은 추출기를 **Executor 노드**([`core/graph/agent_nodes.py`](../../../core/graph/agent_nodes.py))가 쓴다. 지금은 모델이 이 형태를 낼 때마다 실제 제품이 코드 실행에 실패한다.

가리지 않기 위해 **복구 사실을 표시한다.** 복구가 일어나면 `how` 에 `+fused` 를 붙여(`fence+fused`) 평가 결과의 `code_unwrap` 에 남기고, 모델별 붙은 펜스 비율을 계속 기록한다. 즉 **실패율에서는 빼되, 결함 자체는 계속 센다.**

## 2. 예측 (사전 선언 — 결과를 본 뒤 바꾸지 않는다)

새 모델이 없으므로 "통과/실패" 가 아니라, 교정이 의도한 것만 하고 다른 것은 건드리지 않았는지를 본다.

- **P1: base 는 변하지 않는다.** base 의 붙은 펜스는 0/36 이므로 코딩 실패율이 11.1% 그대로여야 한다. 바뀌면 수정이 의도 밖 영향을 준 것이다.
- **P2: `coding_10` 이 v5·v6 에서 통과한다.** 3/3 실패 → 0/3. 그 결과 v6 코딩은 22.2%(8/36) → **13.9%(5/36)** 가 된다.
- **P3: 잡담·계획·RAG 는 세 모델 모두 변하지 않는다.** 추출기는 코딩 슬롯에서만 쓰인다.
- **P4: 붙은 펜스 발생률 자체는 변하지 않는다.** 모델을 바꾸지 않았으므로 v5·v6 각 3/36 이 그대로 기록돼야 한다. 이것이 "가리지 않았다" 는 증거다.

P1~P4 가 모두 맞으면 교정은 성공이고, **남은 코딩 실패가 다음 데이터 라운드의 표적**이 된다.

P2 가 빗나가면(`coding_10` 이 다른 이유로 계속 실패하면) 이 문항에 결함이 **셋** 겹쳐 있었다는 뜻이다 — v6 에서 둘까지 확인했으므로 가능성을 열어 둔다.

## 4. 다음 라운드(v8) 조건

P2 가 맞으면 v6 의 남은 코딩 실패는 `coding_04` 1건 · `coding_06` 3건 · `coding_02` 1건이고, 모두 **자기 수정 재작성**(구현을 한 번 쓴 뒤 주석으로 의심하고 다시 쓰기 시작해 토큰 상한에서 잘림) 계열이다. 이것은 v6 에서 이미 "학습 데이터에 없고 추론 시점에 생긴다"고 확인됐다(소급 감사 307건 중 1건).

따라서 v8 은 데이터 필터가 아니라 **생성 억제** 쪽을 봐야 한다 — 학습 데이터 코딩의 `import` 시작 비중(23.3%) 조정, 또는 프롬프트·디코딩 파라미터. 구체안은 v7 결과를 보고 v8 노트에 적는다.
