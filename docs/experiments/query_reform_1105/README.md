## 1. 바꾸는 것 — `RAG_QUERY_REFORM=1` (기본 0)

[`core/llm/query_reform.py`](../../../core/llm/query_reform.py) `fill_slots`. 일반 경로에서 첫 거르기 뒤에 돈다.

- **발동:** 거른 뒤 1~4편이고 수치 · 비교 유형(`gate_types`)이 아니다. 5편이면 아무 일도 하지 않는다.
- **검색어:** 질문 · 첫 검색어 · 거르기가 남긴 문서(제목 + `brief_findings` 300자)를 9B 에 주고 영어 검색어 한 줄을 받는다. 프롬프트는 코드의 `PROMPT` 로 고정한다. 온도 0 · seed 0.
- **다시 찾기:** 새 검색어로 `rag.search(top_k=15)` → 첫 검색 15편에 있던 논문을 뺀다 → 같은 `filter_relevant` 를 거친다.
- **합치기:** 거르기가 `n→m` 으로 끝났을 때만 남은 문서를 뒤에 붙이고, 그다음 기존 `_rag_context_top_n_hits(n=5)` 로 자른다. 앞선 문서는 밀어내지 않는다.
- **실패:** 호출 실패 · 검색어 못 씀 · 거르기 `없음` · `못 읽음` 이면 대조와 같다.

**바꾸지 않는 것:** 첫 검색어 · 첫 거르기 · 5편이 찬 문항 · 목록 · 단일 · 비교 경로 · 답 단계. 여러 주제 질문은 대부분 5편이 차서(HU 8/36 · HT 1/25 만 빈 칸) 이 라운드로 풀리지 않는다.

**프롬프트 점검(측정 전):** 측정에 안 쓰는 `external_search_v3` · `v2` 질문의 발동 12문항에서 새 검색어만 봤다. V1(논문 용어를 쓰라)은 `irsc ... multilingual` 처럼 문서 세부로 샜고, V2 · V3(주제 유지)은 첫 검색어와 거의 같았고, V6(핵심어 유지 후 교체)은 첫 검색어와 같거나 빈 경우가 있었다. 주제를 앞에 두고 용어를 2~3개 더하는 V4 로 고정했다. 이 두 세트의 질문은 측정에서 뺀다.

## 2. 방법 ([`run.py`](run.py))

- **문항:** 일반 경로 · 수치 아님 · 비교 아님 · held-out 아님. 같은 질문은 한 번만 센다([filter_input_1104](../filter_input_1104/README.md) 는 D · U 겹침 12쌍을 따로 셌다). 세트 순서를 고정해 돌리다가 **발동 70문항에 이르면 멈춘다.** 세트가 먼저 끝나면 거기까지만 잰다(후보 269문항). 발동 여부는 처리 결과를 보기 전에 정해지므로 이 멈춤 규칙은 결과에 기대지 않는다.
  - 순서: real40 · real2 · H · D · U · HU · HT → judge_none_1103 → survey_gate_1030(old · new) → corpus_er_1029 → corpus_llmeval_1030 → query_glossary_1029 → open_gate_1103 stage1 → topic_split2_1104 single → qcond_1025.
- **문항마다:** `_extract_english_rag_query` → `rag.search(top_k=15, name_query=질문)` → `filter_relevant` → 최종 5편(대조) → 운영 함수 `fill_slots` → 최종 5편(처리). 같은 첫 검색 · 첫 거르기를 쓰는 짝 비교다.
- **재실행:** 발동 4문항마다 `fill_slots` 를 한 번 더 돌려 추가 문서가 얼마나 바뀌는지 잰다.
- **라벨:** 바뀐 문항(추가 문서 1편 이상)의 **대조 최종 문서 + 추가 문서**를 어느 쪽인지 적지 않고 seed 1105 로 섞어 달고, 다 달기 전에는 어느 쪽인지 보지 않는다. 제목 + 초록 앞 1,500자로 매긴다: **2** 질문에 직접 답하는 연구(여러 주제 질문은 하위 주제 하나를 직접 다루면 2) · **1** 같은 주제지만 질문의 조건 · 대상과 다름 · **0** 무관. 같은 문항 · 같은 문서의 [filter_input_1104 라벨](../filter_input_1104/labels.tsv)은 같은 규칙으로 조건을 가리고 달았으므로 다시 쓴다.
- **한계:** 라벨은 Claude 혼자 단다. 답 단계와 구체 설명 질문(162 세트)은 재지 않는다.

**문항 수 (protocol §2.5):** 예상 효과 3:1. 발동 70 중 추가 문서가 붙는 문항 약 75%(점검 세트 V1 에서 5/6), 그중 '2' 수와 '0' 수가 같은 문항 약 40% 로 보면 동점 뺀 문항이 약 30 이다. 3:1(17 필요)은 잡고 2:1(37 필요)은 못 잡는다. 라벨할 문서는 약 270편이다.

## 3. dev 관문 — 측정 전 고정

앞선 문서를 밀어내지 않으므로 '2' 수는 줄 수 없다. 그래서 대조와 처리의 '2' 수 비교는 주 지표로 쓰지 않고, 빈 칸에 들어간 문서가 맞는 쪽이 많은지 잰다.

| 지표 | 기준 |
|---|---|
| **주:** 바뀐 문항에서 추가 문서의 '2' 수와 '0' 수 | '2' 가 많은 문항 > '0' 이 많은 문항, 부호 검정(동점 제외) **양측 p < 0.05** |
| 크기: '2' 를 1편 이상 얻은 문항 | 발동 문항의 25% 이상 — 발동마다 시간을 쓰므로 이보다 적으면 값을 못 한다 |
| 보호 1: 바뀐 문항의 최종 문서 중 '2' 비율 (§2.5) | 처리 ≥ 대조 − 5%p |
| 보호 2: 추가 문서 중 '0' 비율 | ≤ 25% |
| 보호 3: 발동 문항의 추가 시간 중앙(검색어 + 검색 + 거르기) | ≤ 25s |
| 보호 4: `호출 실패` · `못 읽음` | 발동 문항의 ≤ 5% |
| 보호 5: 검색어 못 씀(같은 단어 포함) | 발동 문항의 ≤ 15% |
| 신뢰 조건: 재실행에서 추가 문서가 달라진 문항 | ≤ 10% — 넘으면 이 비교를 믿지 않는다 |

참고로만 적는다: 세트별 승패 · 평균 최종 편수 · 단계별 시간 · 정답 든 문항.

- 모두 통과하면 답까지 재는 held-out(`foundation_1031/heldout.tsv`) 라운드를 따로 사전 등록하고 사용자 결정을 받는다. dev 통과는 채택 근거가 아니다.
- 미달이면 접는다. 플래그는 기본 0 그대로 두고, 코드를 지울지 새 맥미니 비교까지 꺼 둘지는 사용자에게 묻는다.

운영 `.env` · 봇은 건드리지 않고 Chroma 는 읽기만 한다. 측정은 약 1.8시간(문항 약 230 × 21초 + 발동 70 × 18초 + 재실행), 01:00 수집과 겹치지 않게 시작한다.

**해석**
- **주 지표는 문턱이 낮았다.** 거르기를 통과한 문서는 원래 '2' 가 '0' 보다 훨씬 많다(filter_input_1104 갈린 문서 102:29, 이번 추가 문서 34:10). 그래서 주 지표 통과만으로 답이 좋아진다고 말할 수 없다. 묽어지는 정도를 재는 것은 보호 1 이다.
- **추가 문서는 무관한 것이 아니라 덜 직접적인 것이다.** 추가 문서는 '2' 40% · '1' 48% · '0' 12%, 대조 문서는 '2' 57% · '1' 32% · '0' 11% 다.
- **미달 폭이 작다.** 추가 문서 3편의 등급이 '1' 에서 '2' 로 바뀌면 기준을 넘는다. 판정자가 한 명이라 이 정도는 흔들릴 수 있다. 그래도 기준은 측정 전에 정한 대로 둔다.
