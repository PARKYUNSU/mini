# 확인 검증 — 파인튜닝이 비길이 제약 준수를 깎는가 (사전 등록)

- 개설일: 2026-10-02
- **학습 없음.** 문항만 새로 만들어 기존 탐색 신호를 확인한다.
- 선행: [`../constraint_generalize_1002/05_conclusion.md`](../constraint_generalize_1002/05_conclusion.md) — 탐색적으로 `base : v9` 가 **0 : 7, p=0.016**

**이 문서는 문항을 만들기 전에 쓴다.** 커밋 시각이 문항 커밋보다 앞선다.

## 1. 확인하려는 것

[`../constraint_generalize_1002/`](../constraint_generalize_1002/) 에서 비길이 제약 24문항에 대해 이런 결과가 나왔다:

| 비교 | 앞만 실패 : 뒤만 실패 | p |
|---|---|---|
| **base : v9** | **0 : 7** | **0.016** |
| base : v10 | 0 : 4 | 0.125 |

**base 가 7문항에서 이기고 한 번도 지지 않았다.** 그런데 이것은 **사전 등록된 가설이 아니었다** — 그 라운드는 `v9 : v10` 을 보도록 설계됐고, `base` 비교는 부수로 출력된 것이다. 다중 비교 보정도 없다.

**그래서 그 가설로 다시 등록해 새 문항에서 잰다.** 이것이 확인 검정(confirmatory)이다.

의미가 큰 이유: 일곱 라운드가 "파인튜닝이 base 를 해치지 않는다" 를 반복 확인했는데 ([`../README.md`](../README.md)), **옛 54문항이 그 손상을 볼 수 없었기 때문일 수 있다.** 잡담·계획에서 base 가 0% 였으므로 더 나빠질 자리가 없었다.

## 2. 가설

- **H1 (주): 비길이 제약에서 v9 은 base 보다 나쁘다.** 파인튜닝이 줄 수·어휘 제약 준수를 깎는다.
- **H2: v10 도 base 보다 나쁘다.** 방향이 같다면 lr 과 무관한 **파인튜닝 자체의 손상**이다. v10 만 멀쩡하다면 lr 인하가 그 손상을 덜어낸다는 뜻이 된다.
- **H3 (반대 가능성): 0:7 은 우연이었다.** 새 문항에서 방향이 갈리면 이쪽이다.

## 3. 난도 보정 — 목표가 바뀐다

지금까지는 "두 모델을 가르는" 중간 난도를 노렸다. **이번에는 다르다.** 파인튜닝의 **손상**을 보려면 **base 가 통과할 수 있는 문항**이어야 한다. base 가 실패하면 비교 대상도 대개 실패해 정보가 없다 — 지난 라운드에서 base 가 실패한 7문항은 전부 "셋 다 실패" 였다.

- **파일럿은 `base` 로만, 3회 과반으로** 돌린다. 목표는 **base 통과율 75~90%**.
- **문항을 고르지 않는다.** 쓴 것을 전부 채택하고, 파일럿은 **난도 눈금**(줄 수 범위·금지어 폭)만 정하는 데 쓴다.
- 이 방식은 [`../planner_signal_0929/`](../planner_signal_0929/) §2-2 에서 한 번 폐기했는데, **그때 우려는 "문항 선택" 이었지 "눈금" 이 아니었다.** 개별 문항을 결과로 추려내면 편향이지만, 난도 범위를 정하는 것은 검정력 확보다.
- **은퇴 모델 파일럿은 쓰지 않는다.** [`../constraint_generalize_1002/`](../constraint_generalize_1002/) 에서 v5·v6 으로 맞춘 난도가 v9·v10 에 옮겨지지 않아 24문항 중 19개가 양 끝으로 갔다. 파일럿 모델과 측정 모델이 다르면 난도도 다르다.

**이 선택이 결과 방향을 만들지 않는 이유**: 난도는 base 와 파인튜닝 모델에 **똑같이** 적용된다. 같은 난도에서 누가 더 많이 실패하는지가 판정이고, 눈금 선택은 **검정력**에만 영향을 준다.

## 4. 판정 (사전 선언 — 결과를 본 뒤 바꾸지 않는다)

**새 문항 24개 전체**에서 판정한다 (줄 수 8 · 어휘 잡담 8 · 어휘 계획 8). base·v9·v10 을 [`../../../scripts/eval_trio_round.sh`](../../../scripts/eval_trio_round.sh) 로 **같은 세션에서** 잰다.

- **확인 (H1)**: `base : v9` McNemar **p < 0.05** 이고 쏠림이 **base 쪽**(= v9 만 실패가 많다).
  - 이때 `base : v10` 도 같은 방향이면 **H2 확인** — 파인튜닝 자체의 손상으로 본다.
  - `base : v10` 이 유의하지 않거나 반대면 **H1 만 취하고**, lr 인하가 손상을 덜어낼 가능성을 미해결로 적는다.
- **반증 (H3)**: `base : v9` 의 p ≥ 0.05. → 탐색 신호를 **"우연"** 으로 기록하고 [`../protocol.md`](../protocol.md) §3 에 올리지 않는다.
- **판정 불가**: 불일치 쌍이 **6개 미만**. 검정력이 없다는 뜻이므로 **숫자를 해석하지 않는다.**

`v9 : v10` 비교는 이 라운드의 판정 대상이 아니다. 참고로 병기한다.

## 5. 문항 제작 규칙

- 계열: **줄 수(`exact_lines`) 8 · 어휘(`must_exclude`) 잡담 8 · 어휘 계획 8.**
- 지난 라운드에서 **base 가 통과한 설정**을 눈금의 출발점으로 삼는다 — 줄 수는 4·6·7·8·9·10줄, 잡담 금지어는 `입니다`·`세요`·`있`·`것이`·`있는`·`좋은`·`합니다`, 계획 금지어는 `확인하`·`실행하`·`출력을` 계열. **base 가 실패했던 설정**(5·11줄, `하는`, `정리하`, `저장하`, `정리`, `데이터를`)은 피한다.
