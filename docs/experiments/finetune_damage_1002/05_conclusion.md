측정 2026-10-03 02:06 → 06:30 (263분). [`scripts/eval_trio_round.sh`](../../../scripts/eval_trio_round.sh) `yunsur_v9 yunsur_v10 damage150`, 커밋 `e2c8fc1`, 150문항 sha256 `967eeb460559`, 반복 3회, 세 모델 1,350시행. 원본 [`04_eval/`](04_eval/).

## 판정 ([§4](README.md#4-판정-사전-선언--결과를-본-뒤-바꾸지-않는다) 그대로)

```
판정 대상 — 새 비길이 제약 24문항, base vs v9
  둘 다 실패 5 · base만 3 · v9만 4 · 둘 다 통과 12
  → 불일치 7쌍, McNemar p = 1.000
```

**반증 (H3).** 탐색 신호를 **우연**으로 기록하고 [`../protocol.md`](../protocol.md) §3 에 올리지 않는다.

| 비교 (새 24문항) | 앞만 실패 : 뒤만 실패 | 불일치 | p |
|---|---|---|---|
| base : v9 | 3 : 4 | 7 | 1.000 |
| base : v10 | 4 : 5 | 9 | 1.000 |
| v9 : v10 | 3 : 3 | 6 | 1.000 |

**이번에는 "못 쟀다" 가 아니다.** 불일치가 7쌍·9쌍으로 §4 의 기준(6쌍)을 넘겼으므로 검정력이 있었고, 그 위에서 **방향이 갈렸다.** 파인튜닝이 비길이 제약을 깎는다는 증거는 없다.

## 어제와 무엇이 달랐나

| | 2026-10-02 (탐색) | 2026-10-03 (확인) |
|---|---|---|
| 문항 | `chat_17`~`32` · `planner_49`~`56` | `chat_33`~`48` · `planner_57`~`64` |
| base : v9 | **0 : 7** (p=0.016) | **3 : 4** (p=1.000) |
| base 통과 | 17/24 | 17/24 |

base 통과율이 같은데 결과가 뒤집혔다. 차이는 **문항뿐**이다.

어제 신호가 왜 생겼는지는 단정할 수 없지만, 그 라운드가 **`v9 : v10` 을 보도록 설계됐고 `base` 비교는 부수로 출력된 것**이었다는 점이 중요하다. 한 라운드에서 세 쌍 × 네 계열을 보면 **우연히 유의한 것이 나올 자리가 많다.** 다중 비교 보정이 없었다.

**이것이 확인 검정을 돌린 이유이고, 그 값을 했다.** 어제 결론 문서에 "탐색적이며 확정이 아니다" 를 적어두지 않았다면, 지금쯤 "파인튜닝이 base 를 해친다" 가 저장소에 결론으로 남아 있었을 것이다.

## 길이 효과는 네 번째로 재현됐다

같은 세션의 길이 제약 16문항([`../planner_signal_0929/`](../planner_signal_0929/) `planner_33`~`48`):

```
v9 vs v10 — v9만 8 · v10만 0 → 불일치 8, p=0.0078
```

| 세션 | v9만 : v10만 | p |
|---|---|---|
| 2026-10-01 오전 | 10 : 2 | 0.039 |
| 2026-10-01 저녁 | 8 : 0 | 0.008 |
| 2026-10-02 낮 | 8 : 0 | 0.008 |
| **2026-10-03 새벽** | **8 : 0** | **0.0078** |

**네 세션 연속이고 v10 이 한 번도 지지 않았다.** 비길이 제약이 세 번 다 갈린 것과 뚜렷이 대비된다 — **lr 효과는 길이 제약에 특정된다.**

## 그래서 지금 그림

| 제약 | v9 vs v10 | base vs 파인튜닝 |
|---|---|---|
| **길이** (줄당 글자 수) | **v10 이 낫다** — 4세션, p ≤ 0.039 | 유의하지 않음 |
| **비길이** (줄 수·어휘) | 구분 안 됨 (3:3) | **구분 안 됨** (3:4 · 4:5) |

파인튜닝은 비길이 제약을 **깎지도 않고 높이지도 않는다.** lr 인하만이, 그것도 **길이 제약에서만** 효과가 있다.

## 난도는 제약이 아니라 주제×제약이 정한다

base 파일럿에서 같은 제약이 주제에 따라 갈렸다:

| 제약 | 통과한 문항 | 실패한 문항 |
|---|---|---|
| 3줄 | `chat_33` 3/3 | `chat_34` 0/3 |
| `있는` 금지 | `chat_45` 3/3 | `chat_43` 1/3 |
| `것이` 금지 | `chat_47` 2/3 | `chat_44` 0/3 |
| `실행하` 금지 | `planner_59` 3/3 | `planner_64` 0/3 |

[`../constraint_generalize_1002/`](../constraint_generalize_1002/) 에서 네 번에 걸쳐 "제약 값"(줄 수·금지어 폭)만 조정하며 천장과 바닥을 오간 이유가 여기 있다 — **조정 대상이 틀렸다.** 값이 아니라 조합을 봤어야 했고, 그래서 빈도 기반 예측도 빗나갔다.

## 한계

- **반증은 "효과가 없다" 의 증명이 아니다.** 작은 효과가 24문항으로는 안 보일 수 있다.
- 비길이 제약은 `exact_lines` 와 `must_exclude` 두 종류뿐이다. 다른 형식 제약은 재지 않았다.
- 어제 신호가 우연이었다고 단정했지만, 두 문항 집합의 난도 분포가 달랐을 가능성도 남는다 (base 통과율은 같았다).
