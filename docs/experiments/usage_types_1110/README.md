# usage_types_1110: 실사용 질문 중 여러 요소 질문 비율 (정의 먼저, 2026-11-10)

> 검토 답변(audit_1110 `review_1110.md` 에 대한 답, 11-10)의 요청: "실제 사용 로그에서 여러 요소 질문이 얼마나 나오는지 세어 달라. 비율이 높으면 우선순위를 올리고, 낮으면 내린다." 이 문서는 질문을 읽기 **전에** 정의를 고정한다. 판정이 아니라 위치 측정이다.

## 1. 자료

- 봇 큐 `.bridge/agent_bridge.sqlite` 의 `bridge_jobs` 141건 전부(2026-04-03 ~ 11-09, `user_text`). 읽기 전용으로 연다.
- real40 · real2 는 넣지 않는다. 대부분 Claude 가 논문 초록으로 쓴 질문이라 실사용이 아니다(real40 의 실제 질문 6개는 이 큐에 이미 있다).
- 질문 원문은 저장소에 넣지 않는다(저장소가 공개). [`labels.tsv`](labels.tsv) 에는 작업 ID · 유형 · 요소 수만 적는다.

## 2. 정의

**학술 질문:** 논문 · 연구 · 방법을 찾거나 그 내용을 묻는 질문(봇이 문서 근거로 답해야 하는 것). 잡담 · 계획 · 일정 · 코딩 요청 · 봇 사용법 · 일반 상식 · 뉴스 · 날씨는 뺀다.

**유형(eval30_1110 과 같은 이름):**

| 유형 | 정의 |
|---|---|
| NM 특정 논문 | 논문 · 방법 이름을 대고 그 내용을 묻는다 |
| SV 서베이 · 목록 | 한 주제의 연구를 넓게 찾는다(추천 · 목록 · 동향) |
| CP 비교 | 둘 이상의 대상을 한 축으로 견준다 |
| NU 수치 | 특정 결과 수치를 묻는다 |
| **MU 여러 요소** | 서로 다른 근거가 필요한 하위 요청이 둘 이상이다(주제 둘 이상, 또는 한 주제의 서로 다른 측면 — 예: 정의 + 측정 방법 + 사례). 비교에 다른 요청이 더 붙으면 MU 다 |
| EX 설명 | 논문 찾기가 아니라 개념 설명을 원한다 |
| FU 이어지는 질문 | 앞 답에 기대야 뜻이 서는 짧은 질문("그거 더 자세히") |

- MU 는 요소 수(2 · 3 · 4 이상)도 적는다.
- 애매하면 `?` 를 붙이고(예: `MU?`), MU 비율을 하한(분명한 MU) · 상한(MU + MU?)으로 보고한다.
- 같은 질문을 다시 보낸 것(문구가 같은 재전송)은 한 번만 센다.

## 3. 보고

- 학술 질문 수, 그중 FU 를 뺀 수(분모), 유형별 수, **MU 비율(하한 · 상한)**, MU 요소 수 분포.
- 비교용: eval30_1110 은 30문항 중 MU 5(17%), HU40 은 질문 40개 모두 3주제다.

## 4. 한계

- 라벨은 Claude 한 명이 단다. 질문을 쓴 사람은 사용자 한 명이고 141건뿐이다.
- 봇 큐에는 라우터가 RAG 로 보내지 않은 질문도 있다. 이 문서는 라우팅과 상관없이 질문 내용으로 나눈다.

**정리:** 실사용 학술 질문의 약 4분의 1(19–31%)이 여러 요소 질문이다. eval30 의 17% 보다 많다. **10-30 이후의 실제 질문 5개는 모두 여러 요소(2–3요소)** 다. 사용자의 업무 질문(판정자 편향 · 사람 검증 · 방해 문서)이 이 꼴로 온다. 4월의 4요소 질문 4개(작업 74–77)는 같은 키워드 4축을 여러 번 고쳐 보낸 시험이다. 그러니 여러 요소 질문의 우선순위를 낮출 근거는 없고, 최근 추세로는 올려야 한다. 다만 최근 5개뿐이고 사용자는 한 명이다.

**정의에서 벗어난 점:**
- 문구가 같은 재전송 외에, 오타 · 앞머리만 다른 재전송 6건도 같은 질문으로 묶었다(13 → 15 · 35 → 32 · 9 → 10 · 111 · 114 → 115 · 134 → 135). 
- 요청 기준(고쳐 쓴 같은 요청 묶음, `cluster`)은 정의에 없던 보기라 따로 보고했다.
- 작업 44 · 55(논문 분석 + 연구 빈틈 제안)는 빈틈 제안이 같은 논문을 근거로 하므로 `MU?` 로 뒀다. 작업 119(문서 순서 · 개수 영향)도 `MU?` 다.
