## 2. 검토 의견

1. **chatbot 을 통째로 옮길 필요는 없어 보인다.** 메인 Ollama 를 건드리는 것은 기억 추출 호출 하나다. chatbot 은 메인에 두고 **기억 추출만 M2 의 Ollama 로 보내면**(`MEMORY_EXTRACT_LOCAL_URL` 한 줄) 35B 끼어듦이 없어진다. 웹 주소 · DB · T7 · 클라이언트는 그대로라 위험이 훨씬 작다. 초안의 목적(메인 Ollama 깨끗하게)은 이걸로 달성된다.
   - 대안: URL 을 비워 Flash 로 돌린다 — 품질은 오히려 높고(0.391) 가장 간단하지만, 클라우드 호출 비용과 대화 내용이 밖으로 나가는 것을 감수한다(전에 로컬로 바꾼 이유일 수 있음 — 사용자 확인).
2. **M2 에서 9B 급 후보:** `qwen3.5:9b`(이미 있음, 6.6GB · 16GB 에 여유) — 1순위. 그다음 `qwen3:8b` 류(받아야 함). `yunsur_v13` 은 논문 RAG 답에 맞춰 학습해 기억 추출에는 맞지 않을 것. **반복 억제 주의**: 오늘 9B 에서 `repeat_penalty` 1.18 이 한국어를 깨뜨렸다 — 추출 호출 옵션을 같이 본다.
3. **품질 확인 방법:** 11-13 실측과 같은 40 건(정답지 = 실제 저장된 슬롯)으로 `qwen3.5:9b`(M2) 를 돌려 자카드를 잰다. 미리 정할 기준 예: 35b(0.346) − 0.03 이상이면 채택, 아니면 Flash 로. 그 40 건 평가 도구는 chatbot 저장소에서 찾아야 한다(이번에 파일 위치는 확인 못 함). 대화 원문이 들어가므로 결과는 공개 저장소(mini)에 원문 없이 수치만 적는다.
4. **옛 서비스 정리가 먼저다.** M2 에 `com.mini.runscheduler` 가 살아 있어 T7 을 SMB 로 붙이는 순간 **매일 수집이 두 기계에서 같은 DB 에 돈다.** 수집 작업 · 스테이징을 M2 에 두려면 이 셋(runscheduler · telegrambot · chroma)을 먼저 내려야 한다.
5. **스테이징 봇:** 가능하지만 준비가 크다 — 프로젝트 `.venv`(Python 3.12), Chroma 사본(16GB) 또는 SMB, 테스트용 텔레그램 봇 토큰, 별도 `.env`. 16GB 에서 v13(5.8GB) + 임베딩 + Chroma 는 들어간다. 다만 오늘 확인한 것처럼 "회귀 확인"은 저장된 답으로 Ollama 없이 대부분 할 수 있어서, 스테이징 봇의 이득은 "실제 텔레그램 흐름 확인" 쪽이다. 우선순위는 낮게 둔다.
6. **수집 작업을 M2 로:** 좋다. 다만 별도 DB 에 쌓아 메인에 합치는 경로가 지금 코드에 없다(`ingest_classics` · 매일 수집은 운영 Chroma 에 바로 쓴다). 합치기 도구를 새로 만들어야 한다 — 오늘 돌고 있는 collect_1113 이 끝난 뒤 설계.
7. **규칙(버전 맞추기 · 채택 실험은 메인 · 테스트 토큰 분리)** 은 그대로 동의. 모델 해시는 `ollama list` ID 로 이미 확인할 수 있다(위 표: v13 같은 파일).
